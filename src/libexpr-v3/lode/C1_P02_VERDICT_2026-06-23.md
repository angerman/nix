# P0.2 (#141) — Change-1 strictness verdict: RE-SCOPE (below the bar) — 2026-06-23

The pre-committed gate: prototype runtime speculation and proceed to the full
build ONLY if it beats the darwin-4 noise floor; else re-scope.  Decided on
measurement — a prototype can only land BELOW the already-sub-bar ceiling, so the
ceiling measurement is sufficient (don't build to confirm a sub-bar number).

## The two measurements

1. **#140 ceiling** (NIX_V3_STRICT_CEILING): of closure-arg thunks, the static
   `strictArgs` analysis proves 0.1%(ff)/0.03%(M5) strict, but 58.6%/69.8% are
   forced at runtime.  The realizable call-arg ceiling ≈ **100K (firefox) / 134K
   (M5)** thunks = ~3.5% of firefox's 2.88M thunks (direct-call path; undercounts
   curried PAPs).

2. **#141 realized-today A/B** (NIX_V3_NO_FUNC_STRICTNESS + NO_STRICT_CALL_UNTHUNK,
   firefox cumulative thunk count):
   - strictness ON (default): 2,880,002 thunks
   - strictness OFF:          2,889,344 thunks
   - **delta = 9,342 (0.32%)** — the existing static strictness already eliminates
     this; it is tiny.

## Why RE-SCOPE

- **Projection from the ceiling:** even the FULL call-arg ceiling (3.5% of thunks)
  is ~100K × 24 B = 2.4 MB of 586 MB warm RSS = **~0.4% RSS**, and ~100K fewer
  allocs + forces out of 36.86 M opcodes ≈ **~1% CPU** — at/below the darwin-4
  noise floor (~1%, per the tight beat-tw-compare spreads).
- **#142's target is empty:** syntactically-strict positions (if-cond / BinOp
  operands / select roots) are ALREADY evaluated force-in-place by the lowerer
  (opt_strictness does redundant-Force ELIMINATION there — they were never
  MkThunk'd).  So strict-by-default lowering has ~no thunk-allocation headroom.
- **The residual needs disproportionate machinery:** closing 0.32%→3.5% requires
  reaching DYNAMIC callees, and pure speculation is UN-DEOPTABLE-UNSAFE (you can't
  un-force an error/non-termination after the fact).  The sound mechanism is
  optimistic evaluation (step-budget + abort + exception-capture) — a major VM
  subsystem — for a projected ~1% gross win.

**Verdict: cost/benefit fails.**  Change 1 (#141–144) is RE-SCOPED:
- The existing static strictness (0.32% call-thunks + force-in-place for strict
  positions) is the realized win and STAYS (already shipped, default-on).
- #143 (dynamic speculative strictness) — KILL (sub-bar; needs optimistic-eval).
- #142 (strict-by-default lowering) — KILL (target already force-in-place).
- #144 (ship Change 1) — nothing further to ship.

The P0.1 scaffold (LambdaDescriptor::strictArgsMask + NIX_V3_STRICT_CEILING) is
RETIRED per Rule 0 (re-scope → delete; commit reverts the field + instrument;
hello.drvPath byte-id, ABI rebuild of v3-smoke).

## Program impact

Shift weight to the bigger levers, unchanged in priority:
- **Change 2 (HAMT)** — attacks the LARGEST CPU bucket (countDistinct 16–17%) AND
  the largest arena RSS bucket (Bindings 142 MB) on nixpkgs override chains.  Next.
- **Change 4 (JIT)** — attacks dispatch (7–23%).
- Change 3 (env interning) — note CLAUDE.md says env interning is ALREADY
  default-on; verify residual at #145.
- Changes 5/6 — second-heap + page-release, ceiling-bounded, last.

This confirms the program's own thesis check: the thunk population is dominated by
lazy DATA (65.7% unforced), which strictness cannot touch — so the data structure
itself (HAMT) and native codegen (JIT) are where the gap actually closes.
