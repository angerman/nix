# C5 (#155) — Boehm/FFI RCA: Change-5 premise falsified — 2026-06-23

Change 5 assumed the 402 MB Boehm (M1, 14% of M5 RSS) is v3→TW bridge Values from
FFI primop wrappers, reducible by moving the heavy crossings native.  Measure-first
falsifies the premise.

## Measurements (firefox.drvPath, cache-off)

1. **`bridge=0`** (NIX_VM_STATS) — v3 routed ZERO thunks through TW.  Not bridge.
2. **`GC_get_heap_size` is a CONSTANT ~402.9 MB** — appears even for `1+1` (where
   total RSS is 31 MB).  It's Boehm's upfront-mapped (lazily-resident) reservation,
   NOT a workload metric.  ⚠️ My cold/warm/depth measurements that all read 402.9
   were reading this constant — a methodology trap; **do not use GC_get_heap_size
   for Boehm RSS attribution.**  (M1's vmmap "Boehm 402 MB resident" on M5 is the
   real resident high-water.)
3. **`GC_get_total_bytes` (cumulative alloc) IS workload-driven:** `1+1` = **0**;
   firefox = **452 MB**.  So v3 evaluates pure expressions with ZERO TW allocation,
   but firefox churns ~431 MB of TW (Boehm) memory.
4. **Per-primop self-attribution** (NIX_V3_BOEHM_ATTR, now retired): the
   STORE-BOUNDARY leaves allocate ~0 — `readFile` 0.0 MB, `pathExists` 0.0 MB.  The
   churn is attributed to the higher-order list primops (concatMap 228, all 96,
   concatStringsSep 25, filter 13, concatLists 10, foldl' 3 MB).

## The artifact + what's actually true

`primConcatMap` etc. are v3-NATIVE (allocList → arena, not Boehm) — so the 228 MB on
concatMap is an **inclusive-attribution artifact**: the main `OP_CALL_PRIMOP` path
does not route through the `invokePrimOpDirect` child-accounting, so native
higher-order primops ABSORB the Boehm their callbacks' subtree allocates.  The TRUE
leaf allocator is obscured.

But two findings are robust (they are correctly-attributed leaves / global counters):
- **NOT the genuine store/FFI boundaries** — readFile/pathExists/derivationStrict
  are ~0 Boehm.  Change 5's "move store primops native" premise is FALSIFIED: the
  store leaves don't allocate the Boehm.
- **NOT bridge thunk-routing** (`bridge=0`).
- It IS ~431 MB of TW allocation under the package-set evaluation subtree, TRANSIENT
  (0.1 MB live at teardown), held resident only by Boehm's macOS no-unmap (same wall
  as #136 arena; BOEHM_TUNING_FALSIFIED 2026-05-27).

## VERDICT — Change 5 RE-SCOPED; #155 partial; precise leaf deferred

- #155: the premise (bridge/store-leaf Values) is FALSIFIED.  The real Boehm source
  is some leaf under the higher-order list-primop subtree, attribution-obscured by
  the inclusive artifact.  Pinning it needs a COMPLETE-attribution instrument that
  hooks the main OP_CALL_PRIMOP path too (the follow-up).
- #156 ("move top-N primops native"): premise gone — the top attributed primops are
  ALREADY native; the store leaves are ~0.  RE-SCOPED pending the precise leaf.
- #157: nothing to ship for Change 5 yet.
- **Overlap with the RSS wall:** the Boehm is transient + held by macOS no-unmap —
  the SAME class as #134 (eviction) and #136 (arena page-release).  Even pinning +
  fixing the leaf, the freed TW memory stays resident unless Boehm unmaps (falsified
  on macOS).  So Change 5 is low-ceiling/blocked like the other reclaim levers.

This continues the program pattern: **Changes 1, 3, 5 all measure modest/blocked;
the real levers are Change 2 (HAMT) + Change 4 (JIT).**  The Boehm 402 MB is largely
a measurement artifact (constant reservation) + transient no-unmap-held TW churn,
NOT a clean reducible bridge-Value bucket.

Instrument retired per Rule 0 (the per-primop numbers carry the inclusive artifact;
a correct version must hook all primop-invocation paths).
