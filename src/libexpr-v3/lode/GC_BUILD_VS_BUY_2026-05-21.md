# GC Build-vs-Buy — Should we keep hand-rolling, or adopt an existing GC?

**Date**: 2026-05-21.
**Question**: We've already partially built our own Cheney nursery (Phase A
allocator + Phase C scavenger landed). Should we continue, or adopt an
existing GC library? Specifically: GHC has its own GC — could we use that?
Are existing GCs even a good fit for Nix's workload?
**Companion doc**: `BOEHM_DEPENDENCY_2026-05-21.md` — explains why Boehm stays
regardless of v3's GC choice. This doc explains why we build the v3 side
ourselves rather than adopting an off-the-shelf framework.
**Status**: architectural decision document. The committed roadmap (Stages 3-7
+ candidate Layer 3 in `BOEHM_DEPENDENCY_2026-05-21.md` §4) assumes the
analysis below.

## TL;DR

**Continue hand-rolling the v3 GC for the next 6-12 months.** Ship Stage 3
(nursery default-on with Phase D write barriers). Measure with Phase 1.5.
Revisit Whippet adoption only post-Stage-7 if `BOEHM_DEPENDENCY_2026-05-21.md`'s
Layer 3 trigger condition fires (tenured-leak ceiling > 1 GB on cardano-node
after Stage 3, or Boehm mark-phase > 10% of total eval time after Layer 2).

GHC's GC is not an option — it's RTS-internal, not a library. We're already
copying its *design* (STG thunk states, Cheney nursery, generational structure);
we can't reuse its *code*.

Whippet is the closest off-the-shelf candidate IF we ever switch. MMTk is the
longer-horizon option only if v3 spins out of cppnix entirely.

The decisive factor: **the hard problems we hit (round-1 + round-2 GC audits)
are missed-root problems specific to v3's data structures — `Tag::Slot`, cell
update, `Thunk::shapeCell`, `forceWriteTarget`, bridge thunks. No off-the-shelf
GC framework helps with those; we'd write the same root-scanner / field-walker
code against any framework's API. The framework doesn't save us much.**

## 1. The question and its framing

Two distinct sub-questions:

(a) **Could we reuse GHC's GC** — given the architectural similarity?
(b) **Should we adopt SOME off-the-shelf GC** — given that we've already
started building our own?

Both are worth taking seriously, but they have very different answers.

## 2. Why GHC's GC is not an option

GHC's RTS GC is the prototype for everything in v3's stated vision:

- STG thunk states (`Suspended` / `Blackhole` / `Evaluated` — see
  `closure.hh:82-95`).
- Cheney-style copying nursery per capability (see Marlow et al., ISMM 2008,
  *Parallel Generational-Copying GC with a Block-Structured Heap*).
- Block-structured old generation with optional mark-compact (see Sansom,
  *Combining single-space and generational garbage collection*).
- Write barrier integrated with thunk update.
- Concurrent mark + non-moving old gen since 8.10 (Well-Typed,
  *A Concurrent Garbage Collector for GHC*).
- Sparks for parallel speculation (relevant for candidate Stage 13).

But it is not a library. There is no `libghcgc.so`.

Concrete obstacles:

1. **Closure layout via info tables** generated by the GHC compiler. The GC
   reads layout info from the info table immediately preceding every heap
   object. Our objects don't have info tables; we use Tag::* discrimination
   instead. Reconciling these is a fork-grade rewrite.
2. **Write barriers inlined** into machine code by the GHC code generator.
   The barrier check (`if (tso->dirty_set) ...`) sits inline at every mutation
   site as part of STG → C-- lowering. Not extractable as a "library call".
3. **Calling convention coupling** — TNTC (tables-next-to-code), generic apply,
   eval/apply convention, evacuation hot path. Tightly bound to GHC's calling
   convention.
4. **Process / thread integration** — pthread, eventlog, RTS flags, capability
   structure, scheduler. The GC assumes Haskell's STM-aware runtime.
5. **No published C-callable API** — GHC's `rts/` is internal. Even people
   embedding GHC use `haskell-rts.h` for `hs_init` etc., not GC primitives.

The practical translation: "use GHC's GC" means "rewrite Nix in Haskell." That
project exists (`hnix`) and made a different set of tradeoffs from cppnix; it's
not what v3 is.

**What we DO take from GHC**: the literature. Marlow's papers on parallel and
incremental GC, the STG paper itself (Peyton Jones 1992), the Block-Structured
Heap paper, Sansom's generational paper, the non-moving GC design (Well-Typed).
We crib algorithms, not code.

## 3. The realistic off-the-shelf candidates

Today's options for embedding a GC in a C++ process:

### 3.1 Boehm-Demers-Weiser (status quo)

- **Maturity**: very mature; in use since 1988.
- **Workload fit for Nix**: poor. Conservative (retains pointer-shaped words
  forever; phantom retention scales with arena lifetime). Non-generational
  (no infant-mortality win for Nix's lazy thunks). Non-moving (no compaction;
  fragmentation accumulates).
- **Adoption cost**: already done. cppnix is built on it; v3 piggybacks.
- **Co-exists with**: itself; nothing to integrate.
- **Per `BOEHM_DEPENDENCY_2026-05-21.md`**: stays as long as v3 is a library
  inside the nix CLI process. Process-level overhead is bounded by TW state
  (parser AST + symbol table + store + plugins; ~50-100 MB baseline).

### 3.2 Whippet (Andy Wingo)

- **Maturity**: active beta as of 2024-2025. Wingo blog posts trace the
  roadmap. Guile is migrating to it from Boehm.
- **Designed as**: a Boehm replacement. C library, embeddable. Same API shape
  as `GC_malloc` / `GC_add_roots`. Conservative AND precise modes (incremental
  adoption from Boehm).
- **Algorithm**: mark-region (Immix-style — Blackburn-McKinley PLDI 2008).
  Generational variant in development as of late 2024.
- **Workload fit for Nix**: probably good. Wingo has decades of Scheme/Guile
  GC experience; Whippet is designed for Lisp-like workloads (lots of small
  pointer-dense objects, high allocation rate, GC-cycle dominance — exactly
  Nix's profile).
- **Adoption cost**: ~1-3 months for "drop-in Boehm replacement on v3 tenured
  side"; longer (3-6 months) for precise mode with custom root scanners.
- **Co-exists with**: Boehm. Two separate GCs in one process. cppnix keeps
  using Boehm for TW values; v3 uses Whippet for arena+nursery. The boundary
  is the FFI — bridge thunks would hold pointers from one GC to the other,
  same problem we have today with v3-storage-as-Boehm-root.
- **Risks**: smaller ecosystem; less battle-tested than Boehm; generational
  variant still maturing; few production users at our scale.

### 3.3 MMTk — Memory Management Toolkit (ANU)

- **Maturity**: mature framework (~10 years of academic + industry use).
  Bindings exist for Ruby 3.4, Julia (in progress), V8 research, OpenJDK
  research, .NET research.
- **Designed as**: a GC framework with pluggable algorithms — GenCopy,
  GenImmix, StickyImmix, Immix, MarkSweep, MarkCompact, SemiSpace, NoGC.
  Client provides root scanning + object layout; framework provides the GC
  algorithm.
- **Implementation language**: Rust. Provides C/C++ FFI bindings.
- **Workload fit for Nix**: technically excellent (multiple algorithms, can
  switch with a recompile; benefits from active research; concurrent variants
  available). Less ecosystem fit (Rust toolchain dependency; nix users would
  need rust in the cppnix build closure).
- **Adoption cost**: 6-12 months realistic. The MMTk API surface is substantial;
  integration requires implementing the `VM` trait (root scanning, slot
  enumeration, mutator coordination). Precise roots required (no conservative
  mode for the v3 stack/registers — though MMTk's conservative-stack research
  is improving).
- **Co-exists with**: Boehm, technically. cppnix keeps Boehm; v3 uses MMTk.
  Same boundary problem as Whippet, with the added complexity of the Rust
  toolchain.
- **Risks**: integration cost is high; Rust dependency complicates packaging;
  team has zero MMTk experience.

### 3.4 Hand-rolled (current path)

- **Maturity**: Phase A (allocator) and Phase C (scavenger) landed; Phase D
  (write barriers) is the remaining open work (`NURSERY_PHASE_D_DESIGN_2026-05-18.md`).
- **Workload fit for Nix**: best (designed specifically for v3's `Tag::Slot`,
  cell-update protocol, STG thunk states, bridge thunks).
- **Adoption cost**: already paying. Phase D ~3-4 weeks. Stage 3 ships ~6 weeks
  after Phase D.
- **Co-exists with**: Boehm (kept for tenured-fallback + traceable_allocator
  + TW values).
- **Risks**: forever-our-responsibility maintenance; performance ceiling
  doesn't match Immix-style mark-region collectors; the recent two-round audit
  surfaced 8+ missed-root classes (most now fixed). The error rate of hand-
  rolling is non-trivial.

### Summary table

| GC | Maturity | Nix workload fit | Integration cost | Co-exists with Boehm? | Toolchain dependency |
|---|---|---|---|---|---|
| Boehm (status quo) | very mature | poor | done | n/a | C |
| **Whippet** | active beta | **good** | ~1-3 months | yes (both C libs) | C |
| MMTk | mature | technically good | ~6-12 months | yes (heavier) | **Rust** |
| **Hand-rolled (current)** | Phase A+C landed | **best (Nix-specific)** | already paying; Phase D ~3-4 weeks | yes by design | C++ (own code) |

## 4. What makes Nix's workload unusual

Nix's eval workload differs from typical OOP / Lisp / Smalltalk in ways that
matter for GC algorithm choice:

### 4.1 Extreme infant mortality

Per `project_thunk_all_perf_2026-05-12`: 10.04 M thunks allocated on
hello.drvPath, 3.30 M forced. **66% of allocated thunks are never forced** —
they are pure waste. They get pinned in the arena because we're allocate-and-
leak; a real generational GC would reclaim them at the first nursery scavenge.

The generational hypothesis (Ungar 1984, refined by every subsequent GC paper)
says most allocations die young. In Nix's lazy-immutable world, this applies
*harder* than in OOP: every binary op + every let-binding + every binary primop
allocates a thunk; most of those thunks are speculation that's never realized.

This argues for any generational GC. Doesn't distinguish hand-rolled vs Whippet
vs MMTk.

### 4.2 Bimodal lifetime distribution

A tiny minority of allocations live the entire eval — top-level `pkgs`,
`lib`, `stdenv`, the Symbol table, the module-system state. Everything else
dies within seconds or less.

This argues for a generational design with a *cheap* old-gen scan. Boehm's
conservative scan over the whole arena is expensive precisely because it
treats young and old uniformly. Immix-style mark-region (Whippet, MMTk
Immix) handles this well via the block-level coarse marking.

### 4.3 Immutable values

Closures, Bindings, ListVecs are write-once after creation. The exceptions are:
- Thunk state transitions (Suspended → Blackhole → Evaluated).
- The cell-update protocol (`Thunk::cell` → write back to
  `Bindings::Entry.value` at OP_RETURN; introduced for STG-style indirection).
- The Tag::App memoization slot (`ValuePair::evaluated`, the round-1 RCA).

These are *known, small* mutation sites. The write barrier need only cover
them — a simple "card mark on cell write" suffices. Compare to Java/C# where
every field write is a barrier site.

This is a *significant* simplification vs a general-purpose GC framework's
write-barrier story. We can have a tighter, more targeted barrier than what
Whippet or MMTk give us out of the box.

### 4.4 High pointer density, small objects

Every `Closure`, `Thunk`, `Bindings::Entry`, `ListVec::elems[]` is mostly
pointer-bearing fields. The mark-bit overhead vs allocation cost is bad for
naive non-generational collectors. Mark-region (Immix) handles this well via
8-byte mark words per line.

### 4.5 Single-threaded today

Candidate Stage 13 considers parallel eval (`PARALLEL_EVAL_CAPABILITIES_2026-05-18.md`).
Concurrent / parallel GC matters then. Today, no concurrency means we can
stop-the-world cheaply and don't pay the synchronisation tax that concurrent
GCs require.

### 4.6 Short process lifetime

`nix eval` typically runs for tens of seconds and exits. We don't have a
long-running daemon today. (That's a candidate too, but not committed.) The
GC's amortized behaviour matters less than the worst-case stop-the-world
pause — short-lived processes can tolerate aggressive STW collection.

### 4.7 Tag::Slot indirection

A v3-specific feature: `Tag::Slot` is a Value whose payload is a `Value*`
pointing at another Value (typically a Bindings::Entry.value cell). Used for
STG-style indirection during cell-update + for memoization across forces.

No off-the-shelf GC knows about this. Each one would need a custom field
walker that says "for Tag::Slot, dereference and follow." That's the same
code we'd write against a Whippet API or against our own scavenger.

## 5. Why hand-rolling is right *for now*

Five concrete reasons:

### 5.1 The architectural design IS GHC's RTS

We're not inventing; we're applying well-published designs in C++. Cheney
nursery + STG thunk states + generational tenured + write barriers — every
piece has decades of literature.

Risk is *execution*, not *design*.

### 5.2 Phase D is a one-time cost

`NURSERY_PHASE_D_DESIGN_2026-05-18.md` scopes Phase D at ~3-4 weeks for a
card-table or per-Bindings dirty-bit barrier. Once landed, the marginal cost
of further GC work is small. Stage 3 ships ~6 weeks after Phase D.

Switching to Whippet *now* means deferring those 3-4 weeks AND paying ~1-3
months of Whippet integration. The total schedule slips by 2-3 months for
modest expected gain.

### 5.3 The hard problems aren't GC-algorithm problems

The recent two-round GC audit (`RCA_VALUEPAIR_EVALUATED_2026-05-21.md` +
`GC_AUDIT_ROUND_2_2026-05-21.md`) surfaced 8+ missed-root classes:

- ValuePair::evaluated (round-1 primary RCA)
- importCache.results, bridgeThunkCache, g_cachedCallFlake.closureValue
- Thunk::shapeCell, CallFrame::forceWriteTarget
- forceDeep / printNixValueRich C-stack hazards
- Auditor-vs-Scavenger mirror gap
- Blackhole-state tail[] not walked across exception revert
- transitive CU `attrSelectCache` walk gap

**Every one of these is a v3-specific structural detail**. A generic GC
framework wouldn't help: it would still need root walkers we'd have to
write, it would still miss roots the same way unless we tell it about them.
The framework abstraction doesn't save us from the hard problems.

What WOULD help is the `V3_DBG_NURSERY_BRUTE` diagnostic infrastructure we
already have (per `GC_AUDIT_ROUND_2_2026-05-21.md` §3 "Tooling findings") +
wiring it into CI (Phase 1.7 R1). That's a few days of work that catches
this entire class of bug mechanically. The diagnostic infrastructure is
the actual mitigation, not the framework choice.

### 5.4 Boehm interop dominates

Per `BOEHM_DEPENDENCY_2026-05-21.md`: Boehm stays as long as cppnix is in
the process. Whichever GC we adopt has to coexist with Boehm, not replace
it. Whippet's API is closest to Boehm; the migration path is "same calls,
different library." MMTk is heavier. Hand-rolling doesn't even have this
problem — we kept Boehm for tenured intentionally.

### 5.5 The cost of a wrong switch is higher than the cost of continuing

If Phase D takes 6 weeks instead of 3-4 (worst case), we still ship Stage 3.
If a Whippet/MMTk integration runs into edge cases at month 3 of 6, we may
not ship at all — and we've delayed Stage 4-7 by that much.

The asymmetric risk profile favours continuing on the path with known costs.

## 6. The cost of off-the-shelf adoption

Even Whippet, the best-fit off-the-shelf candidate, doesn't know about
v3-specific structures:

- **Tag::Slot indirection** — a Value* pointing to another Value*; needs
  custom field walker.
- **Cell-update protocol** — `Thunk::cell` → write back to
  `Bindings::Entry.value` at OP_RETURN; needs custom root + barrier site.
- **Thunk::shapeCell** — Phase 1.5 in-progress shape publishing; needs
  custom field walker (currently missed even by our own scavenger;
  recently surfaced as Round-1 finding #5).
- **Bridge thunks** — `bridgeSrc` pointing to TW `nix::Value*`; needs to be
  registered as a root for cppnix's Boehm (the same problem we have today).
- **valueStack / withStack / vm.frames** — the root set; needs custom
  scanner.
- **CompilationUnit::attrSelectCache** — cached `(Bindings*, slot)` pairs;
  needs custom root walker (Round-2 finding N3 already shows we miss this
  one ourselves).

We'd teach any framework about all of these via custom code. **That's exactly
what we already write.** The framework abstraction wouldn't save much.

There IS one thing a framework saves: the *algorithm* implementation —
write barriers, scavenger inner loop, mark phase, free-list management.
That's real work, but it's a one-time investment we've already partially
made. The total LoC of `gc.cc` + nursery + `alloc.hh::Arena` is ~1200 LoC.
That's not a lot to maintain.

## 7. When to revisit

Per `BOEHM_DEPENDENCY_2026-05-21.md` §9 commitment criteria:

> Layer 3 (Whippet tenured) becomes a serious candidate IF Phase 1.5 + Stage 3
> measurements show:
> - Tenured-leak watermark > 1 GB on cardano-node after Stage 3 ships, OR
> - Boehm mark-phase > 10% of total eval time after Layer 2.

Concretely: ship Stage 3, run the Phase 1.5 measurement spike with the
profiler (`NIX_PROFILER_DESIGN_2026-05-21.md`) + the time-series tool
(`PERF_TRACE_TOOL_DESIGN_2026-05-20.md`), see the numbers.

If the trigger fires, the candidate stage is "Stage 16 — v3 tenured GC:
Whippet adoption", added to `## Candidate future stages` in
`ROADMAP_TO_VISION_2026-05-15.md` with its own design doc.

If the trigger doesn't fire (Stage 3 + Layer 2 brings RSS into acceptable
range), off-the-shelf adoption is "perf nice-to-have" not "structurally
required." Continue as-is; revisit once-per-year quarterly.

## 8. Long-horizon: what changes if v3 spins out of cppnix

The calculus shifts dramatically IF v3 ever becomes a *standalone* Nix
evaluator (no cppnix dependency, like `tvix` is going):

- No Boehm in the process → no interop constraint.
- Process-wide GC choice is unconstrained.
- The Whippet/MMTk decision becomes "what's our GC?" rather than "which
  library do we add alongside Boehm?"
- Custom parser + custom store → much narrower FFI surface → easier to make
  the v3 GC precise (no `nix::Value *` floating around).

That's a different roadmap. Today's roadmap explicitly assumes "v3 is a
library inside cppnix" through Stage 8. Spin-out is a candidate Stage 17
that would be added IF the project decides to fork. That decision has its
own meta-criteria (community / packaging / users), not just GC design.

If/when spin-out becomes serious, MMTk becomes more attractive (its mature
algorithm library + active research benefits dominate when not constrained
by interop). For now: premature.

## 9. Falsifiable claims (Rule 0)

This document commits to:

1. **GHC's GC is not extractable as a library.** Falsified if someone
   produces a working C-callable `libghcgc` binding within a year. Mitigation
   if falsified: re-evaluate as a candidate, primarily for the concurrent
   non-moving design.

2. **The round-1 + round-2 missed-root bug classes are NOT addressed by
   adopting an off-the-shelf GC.** Falsified if Whippet/MMTk integration
   demonstrably catches one of the eight Round-1 classes mechanically (e.g.,
   their type system or compile-time analysis prevents the bug). Mitigation
   if falsified: re-prioritise the switch.

3. **Phase D + Stage 3 ships in ≤ 8 weeks total.** Falsified if Phase D
   exceeds 6 weeks or Stage 3 exceeds 8 weeks of focused work. Mitigation if
   falsified: pause Stage 3, do a focused architectural review, consider
   whether the Cheney + Boehm hybrid is the right shape.

4. **Hand-rolled adds ≤ 1200 LoC of GC code total.** Currently at ~1000 LoC
   (`gc.cc` 670 + `Nursery` 300 + `Arena` 200 in alloc.hh). Phase D
   write-barrier code adds ~300-500 LoC depending on shape. Falsified if
   Phase D code exceeds 1000 LoC by itself. Mitigation: review for hidden
   complexity that argues for framework adoption.

5. **The Whippet/MMTk trigger condition is decidable from Phase 1.5
   measurement.** Falsified if Phase 1.5 measurements turn out to be
   ambiguous (e.g., the bench workloads don't represent real usage).
   Mitigation: add more representative workloads to the measurement set.

## 10. Self-critique

**Critique 1**: this document is suspiciously aligned with "continue doing
what we're doing." Confirmation bias risk. To mitigate: explicitly write up
the strongest case AGAINST hand-rolling.

The strongest case AGAINST: GC bugs are notoriously expensive (each missed
root in the audit took days to diagnose; the ValuePair::evaluated bug pinned
hello.drvPath under scavenge for weeks). A framework with mature tooling
(MMTk's harness, Whippet's diagnostic mode) would prevent a class of these
bugs. The team's velocity might be 2-3× higher with framework support, even
accounting for the integration cost. *This is a real concern.* Mitigation:
land the diagnostic-in-CI work (Phase 1.7 R1) first; if `V3_DBG_NURSERY_BRUTE`
+ stress-test mode catches the next bug class mechanically, the framework
case weakens.

**Critique 2**: assuming Whippet stays viable. Wingo is one person; if Whippet
loses maintenance momentum the calculus changes. Mitigation: this document's
Whippet recommendation is *conditional* on its 2027 maturity; reevaluate when
the trigger fires.

**Critique 3**: the "5.3 hard problems aren't GC-algorithm problems" argument
is partially load-bearing on the assumption that future bug classes will be
similar to the ones we've already seen. If Stage 4 (uniform STG-shape) or
Stage 5 (hidden classes) introduces a fundamentally different bug class —
say, race conditions in concurrent mark — the framework's mature handling of
that class might dominate. We can't know until we get there.

**Critique 4**: the integration cost estimates (1-3 months Whippet, 6-12
months MMTk) are eyeballed from public docs + GC-REVIEW.md, not from anyone
on the team having actually integrated either. A 2-week spike with a real
integration attempt would sharpen these numbers significantly. **Worth doing
once the Phase 1.5 measurement returns**, to make the eventual decision data-
driven.

**Critique 5**: this document doesn't address ergonomics for contributors.
Cppnix users contribute to v3's C++ code. A switch to MMTk (Rust) raises
the contributor bar; Whippet keeps it C/C++. Worth noting; not decisive.

## 12. Decision summary

| Question | Answer | Trigger to revisit |
|---|---|---|
| Reuse GHC's GC? | **No** — RTS-internal; reuse via literature only. | If GHC publishes a C-callable extraction (unlikely in 2026-2027). |
| Adopt Whippet for tenured? | **Defer until post-Stage-7.** | Phase 1.5 + Stage 3 measurement: tenured-leak > 1 GB on cardano-node OR Boehm mark-phase > 10% after Layer 2. |
| Adopt MMTk? | **Defer indefinitely.** Premature given the Rust toolchain dependency and integration cost. | Either: (a) cppnix introduces a Rust dependency anyway (e.g., for libfetchers), OR (b) v3 spins out of cppnix entirely. |
