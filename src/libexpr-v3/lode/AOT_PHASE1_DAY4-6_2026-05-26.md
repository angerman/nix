## What landed

`src/libexpr-v3/bench/build-aot-cache.py` consumes a `NIX_V3_AOT_BUILD_MODE` manifest + the v3 SQLite cache DB and produces a single content-addressed flat file ready for mmap distribution.

End-to-end demo on hello.drvPath:
```
  manifest: 268 (table, key) pairs from cold eval
  → 268 blobs fetched from ~/.cache/nix/v3-bytecode-v3.sqlite
  → 29,172,489-byte flat file
  sha256: d3393bf3c4f46eec1ec2f0c3aedf6c12d3ccb8a3dfbbfa4edf1a4492834720c2
  verify OK: 268 entries, 29172489 bytes
```

## File format v1

```
Offset       Size  Field
-----------  ----  ---------------------------------
0            8     Magic: "V3AOTC01"
8            4     Format version: u32 = 1
12           4     Entry count: u32 N
16           56*N  Entry table (sorted-by-key)
                   per entry:
                     0  32  key (SHA-256 cache key)
                     32  4   table_id (1=CompUnits, 2=EvalResults)
                     36  4   _pad (zero)
                     40  8   blob_offset (u64, absolute)
                     48  8   blob_length (u64)
16+56*N      var   Blob data (concatenated, per entry order)
```

Entries are sorted by `key` so the reader can binary-search by key without an additional hash index. File is content-addressed by SHA-256 of all bytes — that's the natural distribution key.

## Design decisions (with rationale)

- **Sorted-key index, not hash table**: 268 entries on hello.drvPath; log2(268) ≈ 8 comparisons per lookup. For hash table, the constant factor matters less but the format gets a separate probe path. Sorted is simpler.
- **u64 offsets** (not u32): hello.drvPath is 29 MB but cardano-node M5 / haskell-nix-example could push past 4 GB if everything was cached. u64 is the right ceiling.
- **table_id as u8 widened to u32 with pad**: lets us add tables (3, 4, ...) without bumping format version. The current 2 tables fit in u8 but the pad gives room.
- **Embedded `_pad` in entry, not packed**: 56 B is a clean cache-line-friendly multiple; readers may scan many entries during binary search.
- **Manifest dedup** in `parse_manifest`: same (table, key) appearing twice in the manifest (from two cold runs with cache cleared between) is treated as one entry. First occurrence wins.
- **DB-missing blobs are warnings, not errors**: an AOT build right after a cache eviction may have manifest entries that the DB no longer contains. Skip those + warn; the resulting file is still valid (just smaller).

## Verify mode

```
build-aot-cache.py --verify <file>
```

Checks:
- Magic + format version match
- All entries are key-sorted (strictly ascending)
- Each entry's `blob_offset` equals the running cursor (no gaps, no overlap)
- File ends exactly at the last entry's end (no trailing junk)
- SHA-256 of the full file

Used by Phase 1 Day 10-12 client-side fetch validation.

## What Day 4-6 DOESN'T do (next steps)

- **No mmap reader yet** (that's Day 10-12 client work). The flat-file format is designed for mmap'd binary-search reads, but the C++ side of v3 doesn't load AOT files yet.
- **No HTTPS distribution endpoint** (Day 7-9). The file is locally produced; downstream tooling (S3 upload, signing, fetch) is the next sub-task.
- **No deltas / incremental builds**. A fresh AOT cache is produced from scratch each invocation. For nightly cron use, the manifest can accumulate and `build-aot-cache.py` dedups; but content-changed blobs (rare given keys are content-hashes) aren't currently overwritten — first one wins.
