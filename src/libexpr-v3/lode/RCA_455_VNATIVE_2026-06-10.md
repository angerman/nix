# #455 RCA (2026-06-10) — the CURRENT, v3-native manifestation

> ## ✅ RESOLVED (2026-06-10)
> **Root cause:** `OP_CALL_PRIMOP`'s strict-arg scan (vm.cc ~10615) treated every
> `Tag::App` arg as "needs forcing" and rewound to force it — but an **under-applied
> closure-PAP** (`Tag::App` spine bottoming in a closure that still needs args) is
> already WHNF, so `OP_FORCE` returns it unchanged; the scan re-checked, saw the same
> `Tag::App`, rewound, and **looped forever**. `map (f arg) xs` where `f` is a
> partially-applied sibling of a SEPARATELY-IMPORTED `rec` module builds arg0 as exactly
> such a PAP (inline it builds a `Tag::Closure` PAP, which the scan already skipped).
> **Fix (1 line):** skip the force path for an arg that is an under-applied closure-PAP
> (`if (t == Tag::App && isUnderappliedClosurePap(a)) continue;`) — a PAP is a value, the
> primop applies it per element. **Result:** `(import nixpkgs {}).hello.name` →
> "hello-2.12.3" / `.lib.version` → "26.11pre-git" (was: spin); lang **142/143** unchanged;
> v3-smoke ALL PASS; run-455-tests.sh 4/4 PASS. The whole narrowing below stands as the
> RCA trail; the fix landed at the `OP_CALL_PRIMOP` arg-scan, NOT the rec-slot opcode.

**The 35-day-old root-cause note (`project_455_root_cause` memory) is STALE** — it
describes the TW-primary `__v3_call_bridge_1` / `NIX_USE_V3` hook architecture, which
is gone (v3-direct is now the path; the bridge cycle is dead). This is the current RCA.

## Symptom

`v3-eval --expr '(import <nixpkgs> {}).<anything>'` (or even `builtins.typeOf (import
nixpkgs {})`) does **not terminate** — wall-capped at 15–30 s — where TW completes in
< 1 s. This blocks the firefox/real-eval RSS measurement (and L4) for Lever B.

## What it is NOT (hypotheses killed by measurement, 2026-06-10)

- **Not pure `lib`.** `(import nixpkgs/lib).version` = "26.11pre-git", `lib.fix (self:
  {a=1;b=self.a+1;})` = `{a=1;b=2;}` — instant, correct.
- **Not the generic fixpoint machinery.** `lib.extends` (1-overlay), `makeExtensible`,
  `.extend`, `composeExtensions` all evaluate instantly + correctly in isolation.
- **Not the dead TW bridge** (`__v3_call_bridge_1` removed) — pure v3-direct here.
- **Not blackhole-as-value** (`NIX_V3_NO_BLACKHOLE_AS_VALUE=1` — no change) nor the
  **force-chain reentry detector** (`NIX_V3_FORCE_CHAIN_REENTRY_MAX=2`, `…_DEPTH=40` —
  no change): the cycle does not flow through those primop paths.
- **Not eager-forcing** (`NIX_V3_NO_EAGER_FORCED_LET=1`, `NIX_V3_EAGER_ARG_FORCE=0`
  (default-off anyway), `NIX_V3_NO_DEEP_FORCE=1` — no change).

## What it IS

The **package-set OUTER fixpoint** — `pkgs = boot stages` where
`pkgs/stdenv/booter.nix` does `pkgs = dfold folder postStage (_: {})
withAllowCustomOverrides` (booter.nix:165).

- **Alloc signature at the wall-cap: `closures=71, attrsets=54, thunks=0`,
  non-growing** over 15–30 s ⇒ a true non-terminating **force recursion** (allocating
  nothing new), hit **early** — before any thunk-allocating package body, i.e. purely in
  the **outer stage-application machinery**. (`71 closures` matches the old memory's "71
  closures" observation — same point.)
- **Sample (idle, 6 s) = one deep growing C-stack**, repeating:
  `dispatchLoop → forceValue(vm.cc:13019) → dispatchLoop → callClosure(vm.cc:13250) →
  forceValue → dispatchLoop …`, cycling through op-handlers **OP_CALL / OP_CALL_N /
  OP_TAIL_CALL[_N]** (application) + **OP_ATTRS_HAS** (`?`/`or`) → `callClosure` →
  re-force. C-stack-growing recursive re-descent, not a tight inner loop.

### Mechanism (from booter.nix `dfold`, lines 62–80 + postStage 142–163)

`dfold` is a call-by-need doubly-linked fold; its own comment (line 72): *"Note the
cycle — call-by-need ensures finite fold."* The fold builds
`cur = op pred x succ; succ = go cur (n+1)` (mutually recursive) — **finite ONLY if
laziness leaves `succ`/`nextStage` unforced** until needed. `postStage`/stdenv.cc
resolution (lines 150–153) documents a **deliberately-avoided infinite recursion**
(`buildPackages.clang` checking `targetPackages.stdenv.cc`) that nixpkgs sidesteps
*statically* to stay lazy.

⇒ **#455 = a force-ORDER divergence**: v3 forces a value (a `nextStage`/`succ`
reference, or the avoided `stdenv.cc` branch — surfaced via OP_CALL*/OP_ATTRS_HAS) that
TW's specific call-by-need order leaves unforced, turning the intended-finite fold into
an infinite recursion. v3 is not categorically more eager (it allocates 0 thunks because
the loop precedes thunk-heavy eval); it diverges on *one specific* WHNF whose v3
force-order cycles.

## Why a minimal repro hasn't fallen out yet

A bare `dfold` + 3 stub stages + a `postStage` that reads `cur.cc` **terminates** in v3
(returns the right answer). The trigger needs the *specific* cross-compile platform /
`stdenv.cc isClang` / `adjacentPackages` mutual-reference shape. Reproduction is the
open sub-task (the writable bisect copy is at `/tmp/nixpkgs-bisect`).

## Bytecode-level localization (2026-06-10, V3_DBG_TRAP_ON_LIMIT)

`V3_DBG_TRAP_ON_LIMIT=1` dumps the VMState frame stack + bytecode at the wall-cap. Key
findings — it is **NOT unbounded C-recursion** (that would SIGSEGV; it runs the full
15 s): it's a **bounded ~10-frame re-entrant force loop that never progresses**
(`frames=10, valueStack=101`), with **one CU re-entered 3× at different IPs** (the
looping function).

The looping frames live in **`pkgs/top-level/default.nix`** (bytecode constant names:
`stages`, `throwIfNot`, `pkgs`, `checked`, `__allowFileset`). The hot frame returns
**`checked pkgs`**:
```
ip167 OP_APPLY_OVERRIDES
ip169 OP_REC_BINDING_SLOT_REF operand=226 data=[0]  ; checked   → SET_LOCAL 10
ip173 OP_REC_BINDING_SLOT_REF operand=212 data=[1]  ; pkgs      → SET_LOCAL 11
ip176 OP_GET_LOCAL2 (10,11)
ip177 OP_TAIL_CALL                                              ; checked pkgs
```
⇒ the cycle runs through **`OP_REC_BINDING_SLOT_REF` + `OP_APPLY_OVERRIDES`** — the
rec-attrset / fixpoint-slot machinery — while forcing the top-level package-set rec
bindings (`pkgs` / `checked` / `lib` are entries of top-level's big `let rec … in`).

**This matches the known bug class** flagged in `project_495_intrinsics` (reviewer
hypothesis): **"C2 — OP_APPLY_OVERRIDES rec-slot semantic-staleness"** + the
broader-thunkify upvalue bug = the same class = **stale slot/upvalue references after a
structural change**. The pkgset fixpoint re-forces a rec-binding slot whose v3
resolution cycles where TW's lazy slot resolution terminates.

## MINIMAL REPRO (2026-06-10) — no full pkgset needed

```
((import <nixpkgs>/lib).systems.elaborate "x86_64-linux").system
```
**v3 spins** (closures=30/attrsets=41/thunks=0, non-growing); **TW = "x86_64-linux" in
0 s**. Even `builtins.isAttrs (elaborate "x86_64-linux")` spins — v3 cannot reach the
**WHNF** of the elaborated set. `parse.mkSystemFromSkeleton`/`mkSkeletonFromList` alone
work; the cycle is `elaborate` specifically. Saved as
`test/repro-455-systems-elaborate.nix`. (The pkgset hit this because forcing
`stdenv.hostPlatform` elaborates the platform via `lib.systems.elaborate`.)

`elaborate` (lib/systems/default.nix:83) returns a big **self-referential rec-attrset
`final`** built as a `//` chain whose RHS operands are **functions of `final`**:
```
final = { …; libc = if final.isLinux then "glibc" else …; … }   # base fields ref overlay fields
      // platforms.select final                                  # :305  (fn of final)
      // mapAttrs (n: v: v final.parsed) inspect.predicates      # :422  (adds isLinux/isx86/…)
      // mapAttrs (n: v: v final.gcc.arch or "default") …        # :423
      // args                                                     # :424
      // { rust = …; … };                                         # :425
```
So forcing `final` to WHNF must WHNF the `//`-chain, whose operands read fields of
`final` (which are spread across base + later overlay layers). v3's `//`-chain /
APPLY_OVERRIDES WHNF order re-enters where TW's lazy merge terminates.

- `final = base // (g final)` where `g` reads `final.a` ✓
- `final = base // mapAttrs (v: v final.a) preds` ✓

- (`final = base // (if final.a==1 …)` is a GENUINE cycle — both v3 AND TW error; correct.)

⇒ the trigger needs the *specific* elaborate combination (multiple `//` layers +

`linker` referencing many overlay-added `isX` flags).

## NARROWED to a 1-line repro (2026-06-10) — `lib.strings.splitString`

The cycle is reached EARLY (in `elaborate`'s use of `parse.mkSystemFromString`, which
parses the *string* "x86_64-linux"). Drilling in (each spins in v3 / instant in TW):
```
lib.systems.elaborate "x86_64-linux"                  ~30 closures
→ lib.systems.parse.mkSystemFromString "x86_64-linux" ~16
→ lib.strings.splitString "-" "x86_64-linux"          ~10   ← TIGHTEST 1-line repro
```
`mkSystemFromString = s: mkSystemFromSkeleton (mkSkeletonFromList (splitString "-" s))`;
`mkSkeletonFromList [list]` works, so it's `splitString`.

**The decisive finding: it is NOT the splitString logic.** ALL of these evaluate
CORRECTLY + instantly in v3:
- the splitString body inline (with `sep`/`s` as `let` vars);
- a standalone `rec { …escapeRegex…addContextFrom…splitString… }` lib (`/tmp/sslib.nix`);
- a standalone *fixpoint* lib `lib = { strings = mod { inherit lib; }; }` (`/tmp/sslib2.nix`);
- `builtins.split` / `filter isString` / `map (addContextFrom s)` / `escapeRegex` / `escape`
  each in isolation; AND other lib.strings members (concatStringsSep/hasPrefix/removePrefix/
  toUpper/stringToCharacters) accessed through the real lib.

**Only `lib.strings.splitString` (and `lib.splitString`) — the function as COMPILED inside
the FULL nixpkgs lib — spins.** `NIX_V3_NO_DISK_CACHE=1` does not help.

Cleanest trap dump (`lib.strings.splitString "-" "x86_64-linux"`, frames=2): splitString's
body reaches `map (addContextFrom s) splits` (`OP_CALL_PRIMOP map`); the `splits` thunk
(`OP_MAKE_THUNK "splits" data=[3,0]`) captures **upvalue0 (= `escapeRegex`) + sep + s**;
forcing `splits` (= `filter isString (split (escapeRegex …) …)`) loops.

⇒ **ROOT CAUSE (localized): a mis-resolved UPVALUE in the compiled lib function** — the
identical source works in every standalone shape, so the divergence is v3's *compilation*
of `splitString` as a member of the full nixpkgs lib, where its captured `escapeRegex`
upvalue (or the `splits` thunk's upvalue list) resolves wrongly. This is the
**#495 "lib lowered twice / v3SubExprCache keeps first module's bytecode → second
lowering's MAKE_THUNK upvalue-arity mismatch"** class ([[project_495_intrinsics]]).

### Standalone kernel (2026-06-10) — `map (f arg)` over an imported rec-sibling

Reduced below splitString to a **~5-closure, 2-file, nixpkgs-FREE** kernel (committed as
`test/repro-455-mod.nix` + `test/repro-455-import-papmap.nix`):
```
# repro-455-mod.nix:   { lib }: rec { f = a: b: a + b; ss = map (f "x") [ "a" "b" ]; }
(import ./repro-455-mod.nix { lib = {}; }).ss     # v3 SPINS;  inline → [ "xa" "xb" ]
```
Toggle results: `map (f "x") list` SPINS (imported); `(f "x") "a"` (no map) works;
`map f list` (not partial) works; the SAME module **inlined** (`let m = rec {…}; in m.ss`)
works. So the trigger = **`map` (a primop) applied to a PARTIALLY-APPLIED sibling of a
SEPARATELY-IMPORTED `rec` module** (cross-CU).

### Mechanism — CORRECTED (opcode exonerated by diagnostic)

A gated diagnostic in `OP_GET_UPVALUE_REC_BINDING_SLOT` showed it fires **exactly once**,
cleanly (`sym=f, attrs.tag=Attrs`) — so the rec-slot resolution is **NOT** the loop
(earlier hypothesis falsified). A `sample` of the spinning kernel shows a **flat** hot
profile dominated by **`applyForceWriteback`** (the OP_FORCE writeback machinery, vm.cc:
2362-2429) across a handful of dispatchLoop ops (7273/7161/7109/10639/10621/3021) — a
tight **re-entrant force-writeback loop** (frames=2, thunks=0, non-progressing). I.e. when
`map` applies the PAP `(f "x")` to an element, forcing the resulting App/Slot **re-forces
the same value forever** (never memoizes / a self-referential Slot chain), but only for the
cross-CU PAP; inline it terminates.

### Concrete next step toward the fix

Instrument the force path for the kernel: in `applyForceWriteback` / the OP at vm.cc:7273,
log the Value (tag + pointer) being force-looped to identify whether it's (a) an `App`
PAP whose `evaluated` memo is never set, or (b) a `Tag::Slot` chain that forces to itself.
The fix is then either App-memo writeback for the map-applied PAP, or breaking the
self-Slot chain in the cross-CU PAP capture — NOT a global change (must keep lang 142/143).
Validate: the kernel returns `[ "xa" "xb" ]`, `lib.strings.splitString` returns
`[ "x86_64" "linux" ]`, `(import nixpkgs {})` terminates, lang 142/143 unchanged
