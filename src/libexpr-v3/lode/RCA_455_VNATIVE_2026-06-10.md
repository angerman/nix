# #455 RCA (2026-06-10) — the CURRENT, v3-native manifestation

**The 35-day-old root-cause note (`project_455_root_cause` memory) is STALE** — it
describes the TW-primary `__v3_call_bridge_1` / `NIX_USE_V3` hook architecture, which
is gone (v3-direct is now the path; the bridge cycle is dead). This is the current RCA.

## Symptom

`v3-eval --expr '(import <nixpkgs> {}).<anything>'` (or even `builtins.typeOf (import
nixpkgs {})`) does **not terminate** — wall-capped at 15–30 s — where TW completes in
< 1 s. This blocks the firefox/real-eval RSS measurement (and L4) for Lever B.

## What it is NOT (hypotheses killed by measurement, 2026-06-10)

- **Not pure `lib`.** `(import nixpkgs/lib).version` = "26.11pre-git", `lib.fix (self:
  {a=1;b=self.a+1;})` = `{a=1;b=2;}` — instant, correct.
- **Not the generic fixpoint machinery.** `lib.extends` (1-overlay), `makeExtensible`,
  `.extend`, `composeExtensions` all evaluate instantly + correctly in isolation.
- **Not the dead TW bridge** (`__v3_call_bridge_1` removed) — pure v3-direct here.
- **Not blackhole-as-value** (`NIX_V3_NO_BLACKHOLE_AS_VALUE=1` — no change) nor the
  **force-chain reentry detector** (`NIX_V3_FORCE_CHAIN_REENTRY_MAX=2`, `…_DEPTH=40` —
  no change): the cycle does not flow through those primop paths.
- **Not eager-forcing** (`NIX_V3_NO_EAGER_FORCED_LET=1`, `NIX_V3_EAGER_ARG_FORCE=0`
  (default-off anyway), `NIX_V3_NO_DEEP_FORCE=1` — no change).

## What it IS

The **package-set OUTER fixpoint** — `pkgs = boot stages` where
`pkgs/stdenv/booter.nix` does `pkgs = dfold folder postStage (_: {})
withAllowCustomOverrides` (booter.nix:165).

- **Alloc signature at the wall-cap: `closures=71, attrsets=54, thunks=0`,
  non-growing** over 15–30 s ⇒ a true non-terminating **force recursion** (allocating
  nothing new), hit **early** — before any thunk-allocating package body, i.e. purely in
  the **outer stage-application machinery**. (`71 closures` matches the old memory's "71
  closures" observation — same point.)
- **Sample (idle, 6 s) = one deep growing C-stack**, repeating:
  `dispatchLoop → forceValue(vm.cc:13019) → dispatchLoop → callClosure(vm.cc:13250) →
  forceValue → dispatchLoop …`, cycling through op-handlers **OP_CALL / OP_CALL_N /
  OP_TAIL_CALL[_N]** (application) + **OP_ATTRS_HAS** (`?`/`or`) → `callClosure` →
  re-force. C-stack-growing recursive re-descent, not a tight inner loop.

### Mechanism (from booter.nix `dfold`, lines 62–80 + postStage 142–163)

`dfold` is a call-by-need doubly-linked fold; its own comment (line 72): *"Note the
cycle — call-by-need ensures finite fold."* The fold builds
`cur = op pred x succ; succ = go cur (n+1)` (mutually recursive) — **finite ONLY if
laziness leaves `succ`/`nextStage` unforced** until needed. `postStage`/stdenv.cc
resolution (lines 150–153) documents a **deliberately-avoided infinite recursion**
(`buildPackages.clang` checking `targetPackages.stdenv.cc`) that nixpkgs sidesteps
*statically* to stay lazy.

⇒ **#455 = a force-ORDER divergence**: v3 forces a value (a `nextStage`/`succ`
reference, or the avoided `stdenv.cc` branch — surfaced via OP_CALL*/OP_ATTRS_HAS) that
TW's specific call-by-need order leaves unforced, turning the intended-finite fold into
an infinite recursion. v3 is not categorically more eager (it allocates 0 thunks because
the loop precedes thunk-heavy eval); it diverges on *one specific* WHNF whose v3
force-order cycles.

## Why a minimal repro hasn't fallen out yet

A bare `dfold` + 3 stub stages + a `postStage` that reads `cur.cc` **terminates** in v3
(returns the right answer). The trigger needs the *specific* cross-compile platform /
`stdenv.cc isClang` / `adjacentPackages` mutual-reference shape. Reproduction is the
open sub-task (the writable bisect copy is at `/tmp/nixpkgs-bisect`).

## What the fix needs (and why it's deep / multi-session)

1. **A runnable TW for a differential force-order trace** (NIX_TRACE_EVAL diff, per
   `project_578_eval_trace`) — pinpoint the EXACT value whose force-order diverges.
   (Blocker today: the only TW build is root-owned `/var/root/iohk-nix/build/src/nix/nix`,
   not runnable as user `angerman`; need a user-runnable TW.)
2. **A targeted force-order / memoization fix** so v3 leaves that value lazy like TW —
   NOT a blind global eagerness change (would risk the 142/143 lang baseline + all eval).
3. Validate: lang 142/143 unchanged + the pkgset fixpoint terminates byte-identically.

This is an architectural force-semantics fix, not a one-commit change. Until pinned via
the differential trace, any "fix" is speculation (Rule 0 / measure-twice).

## Bytecode-level localization (2026-06-10, V3_DBG_TRAP_ON_LIMIT)

`V3_DBG_TRAP_ON_LIMIT=1` dumps the VMState frame stack + bytecode at the wall-cap. Key
findings — it is **NOT unbounded C-recursion** (that would SIGSEGV; it runs the full
15 s): it's a **bounded ~10-frame re-entrant force loop that never progresses**
(`frames=10, valueStack=101`), with **one CU re-entered 3× at different IPs** (the
looping function).

The looping frames live in **`pkgs/top-level/default.nix`** (bytecode constant names:
`stages`, `throwIfNot`, `pkgs`, `checked`, `__allowFileset`). The hot frame returns
**`checked pkgs`**:
```
ip167 OP_APPLY_OVERRIDES
ip169 OP_REC_BINDING_SLOT_REF operand=226 data=[0]  ; checked   → SET_LOCAL 10
ip173 OP_REC_BINDING_SLOT_REF operand=212 data=[1]  ; pkgs      → SET_LOCAL 11
ip176 OP_GET_LOCAL2 (10,11)
ip177 OP_TAIL_CALL                                              ; checked pkgs
```
⇒ the cycle runs through **`OP_REC_BINDING_SLOT_REF` + `OP_APPLY_OVERRIDES`** — the
rec-attrset / fixpoint-slot machinery — while forcing the top-level package-set rec
bindings (`pkgs` / `checked` / `lib` are entries of top-level's big `let rec … in`).

**This matches the known bug class** flagged in `project_495_intrinsics` (reviewer
hypothesis): **"C2 — OP_APPLY_OVERRIDES rec-slot semantic-staleness"** + the
broader-thunkify upvalue bug = the same class = **stale slot/upvalue references after a
structural change**. The pkgset fixpoint re-forces a rec-binding slot whose v3
resolution cycles where TW's lazy slot resolution terminates.

### Concrete next step toward the fix

Identify WHICH rec-binding slot the re-entered CU cycles on (disasm the re-entered CU's
3 active IPs; correlate `OP_REC_BINDING_SLOT_REF operand` → the symbol) and why its v3
resolution re-enters instead of returning the in-progress/memoized slot value. Then a
targeted fix to `OP_REC_BINDING_SLOT_REF` / `OP_APPLY_OVERRIDES` slot-resolution
force-order (NOT a global eagerness change). Validate: lang 142/143 unchanged + the
pkgset fixpoint terminates. v3-native fixpoint slots already work for `with self;`
rec-attrsets (#427 OP_REC_BINDING_SLOT_REF); the pkgset's `let rec` + APPLY_OVERRIDES
shape is the unhandled case.
