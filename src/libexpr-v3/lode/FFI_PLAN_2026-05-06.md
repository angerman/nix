# v3 FFI Surface — Design Plan (2026-05-06)

A clean-room v3 evaluator should depend on the rest of Nix only through
a small, explicit FFI. This document writes out what that interface
looks like, after stress-testing the initial "~30–35 functions" sketch
for holes.

## Goals

- v3 owns: parse → AST → bytecode → VM → values, including all
  evaluation, GC, primop dispatch, and value representation.
- Everything that *cannot* live in v3 — filesystem, network, store
  daemon, derivation registration, persistent caches, settings — is
  reached through the FFI declared here.
- The FFI is callable both directions: v3 calls out for I/O and store
  ops; the store calls back into v3 to apply closures (filter
  functions, etc.).
- The interface should let v3 build and run without `libnixexpr` (the
  tree-walker) at all. It still depends on `libnixstore` and a small
  parser shared library.

## Holes found in the initial sketch

The first pass said "~30–35 functions, four categories." Re-checking:

1. **"Store-IO" was too narrow.** It conflated three concerns:
   filesystem I/O (`readFile`, `readDir`, `pathExists`), network
   fetchers, and store-daemon ops. They share *no* code; each needs
   its own header.
2. **Closure-callback ABI is not one function.** It needs: apply
   (n-ary), error propagation (the closure can throw), and explicit
   re-entrancy depth handling (cf. `NIX_V3_BRIDGE1_DEPTH` today).
3. **Derivation construction is a subsystem, not a primop.** It
   handles fixed-output, content-addressed, structuredAttrs,
   passAsFile, impure, allowedReferences, multiple outputs,
   placeholder synthesis, and `.drv` file writing. The FFI needs a
   record-shaped descriptor, not "one function".
4. **String contexts** are a cross-boundary type, not just opaque
   data. The store consumes them when computing input-addressed drv
   hashes and when validating output references.
5. **Position threading through errors** wasn't addressed. When a
   store op throws, the trace must show the v3 call site. That means
   either passing `PosIdx` on every call or attaching position
   metadata to error objects at the boundary.
6. **Settings access is wider than `EvalSettings`.** v3 reads
   read-only-mode, pure-eval, restricted-eval, allowed-uris,
   substituters, NIX_PATH, current-system, and a few flags. Several
   gate which primops are even legal to call.
7. **Memory management interaction** wasn't decided. Today v3 shares
   Boehm GC with TW. Going standalone forces a choice (keep Boehm /
   arena-only / hybrid).
8. **Flake support** is its own library (`libnixflake`), not part of
   the tree-walker but reached through it today. Needs a separate
   sub-FFI.
9. **`builtins.findFile` recurses into fetchers** when NIX_PATH
   contains URLs. That's not a single store op — it's a small layer
   of its own.
10. **Eval cache / fetch cache** are persistent state across
    invocations (SQLite). v3 already has its own bytecode cache;
    sharing the eval cache requires a stable Value-serialization
    contract.
11. **Logger / activity** is a stateful observer pattern (build
    progress, copying paths). Needs an interface, not just settings.
12. **Sandbox / pure-eval gating** must be enforceable at primop
    dispatch, not "the primop checks settings and refuses." Otherwise
    every primop accumulates the same boilerplate.

Realistic count after holes: **~60 functions plus ~10 types**, spread
across 11 categories. Still small. Writeable as a single header pack.

---

## Out of scope (v3 owns these — never crosses the FFI)

- AST → IR lowering (`lower.cc`), IR → bytecode (`emit.cc`), bytecode
  optimization (`opt_*.cc`).
- VM dispatch loop (`vm.cc`), all opcodes, frame management,
  exception unwinding, blackhole detection, tail-call handling.
- `Value` representation (16-byte tagged), `Closure` layout, `Bindings`
  layout, `Thunk` layout, all GC interaction *within* the value
  domain.
- Primop registry, primop dispatch, lazy-args handling, partial
  application.
- Inline caches (current `OP_ATTRS_SELECT` IC; future shape-PIC).
- Position side-tables (per-attr, per-call).
- String-context side-table (the v3 side; conversion sketched below).
- Disk cache for compiled bytecode (`disk_cache.cc`).

## Categories and signatures

### A. Parser  (5 entries + 1 type)

Shared frontend. `Expr*` is an opaque pointer carrying the AST. v3
walks it once at lower-time and never again.

```c++
struct Expr;  // opaque AST root

Expr * parseExprFromFile(SourcePath path, PosTable & pos, SymbolTable & syms);
Expr * parseExprFromString(std::string_view src, SourcePath origin,
                           PosTable & pos, SymbolTable & syms);
void   bindVars(Expr * e, const StaticEnv & env);  // static name resolution
SourcePath canonicalisePath(std::string_view raw, SourcePath cwd);
const Pos & lookupPos(PosTable &, PosIdx);
```

### B. Symbol & position tables  (6 entries + 2 types)

Pure data, shared because every Expr/Value carries indices into them.

```c++
struct SymbolTable;
struct PosTable;

SymbolId   intern(SymbolTable &, std::string_view name);
std::string_view str(const SymbolTable &, SymbolId);
PosIdx     addPos(PosTable &, Pos);
Pos        lookup(const PosTable &, PosIdx);
bool       eq(SymbolId, SymbolId);
size_t     hash(SymbolId);
```

### C. Filesystem I/O  (5 entries)

Used by `readFile`, `readDir`, `pathExists`, `import` (file lookup),
path interpolation. *Not* store ops — just I/O.

```c++
std::string  readFile(SourcePath);
DirEntries   readDir(SourcePath);
FileType     readFileType(SourcePath);   // regular | dir | symlink
bool         pathExists(SourcePath);
SourcePath   resolveSymlinks(SourcePath);
```

### D. Network fetchers  (6 entries + fetcher input/output types)

Each fetcher is a single call. Caching is the implementation's job
(uses `~/.cache/nix`); v3 doesn't see cache state.

```c++
struct FetchInput;     // tagged union: url, github, git, mercurial, tarball, …
struct FetchResult { StorePath path; Hash narHash; AttrSet info; };

FetchResult fetchurl     (URL, std::optional<Hash> sha256, FetchOpts);
FetchResult fetchTarball (URL, std::optional<Hash> sha256, FetchOpts);
FetchResult fetchTree    (FetchInput);
FetchResult fetchGit     (URL, GitOpts);
FetchResult fetchMercurial(URL, HgOpts);
FetchResult fetchClosure (StorePath, FetchClosureOpts);
```

### E. Store ops  (10 entries + 4 types)

Store-daemon operations. v3 has a `ref<Store>` it acquired at startup.

```c++
struct StorePath;   // opaque
struct PathInfo;
struct NAR;         // streaming type or in-memory blob
struct Hash;

StorePath addToStore     (std::string name, NAR contents,
                          ContentAddressMethod, HashAlgo, References);
StorePath addTextToStore (std::string name, std::string text, References);
StorePath copyPathToStore(SourcePath src, FilterCallback /* see G */);
std::optional<PathInfo> queryPathInfo(StorePath);
bool       isValidPath  (StorePath);
StorePath  parseStorePath (std::string_view);
std::string printStorePath(StorePath);
StorePath  computeStorePath(std::string name, Hash, StorePathType,
                            References);  // "what would the path be"
std::string placeholderFor(std::string outputName);  // for builder env
void       ensureValid  (StorePath);  // realises if substitutable
```

### F. Derivation construction  (3 entries + 2 record types)

The complexity lives in the descriptor record; v3 fills it in by
walking the input attrset.

```c++
struct DerivationDescriptor {
    std::string name;
    std::string system;
    std::string builder;
    std::vector<std::string> args;
    std::map<std::string, std::string> env;        // resolved strings
    std::set<std::string> outputs;                  // {"out"} default

    // Output addressing — exactly one of:
    std::optional<FixedOutput> fixedOutput;        // outputHash, FOD
    bool contentAddressed = false;                  // CA, floating
    bool impure = false;

    // Structured / passAsFile
    bool structuredAttrs = false;
    std::set<std::string> passAsFile;
    std::optional<nlohmann::json> structuredJson;   // when structuredAttrs

    // Constraints
    std::optional<std::set<StorePath>> allowedReferences;
    std::optional<std::set<StorePath>> allowedRequisites;
    std::optional<std::set<StorePath>> disallowedReferences;
    std::optional<std::set<StorePath>> disallowedRequisites;

    // Inputs collected from string contexts of all values above
    std::set<StorePath> inputSrcs;
    std::map<StorePath, std::set<std::string>> inputDrvs;
};

struct DerivationOutputs {
    StorePath drvPath;
    std::map<std::string, StorePath> outputs;       // "out" → /nix/store/...
    std::map<std::string, std::string> placeholders; // before realisation
};

DerivationOutputs instantiateDerivation(const DerivationDescriptor &);
Derivation        parseDerivation     (StorePath drvPath);  // for `import x.drv`
StorePath         writeDerivation     (const Derivation &); // round-trip
```

`instantiateDerivation` is the moral equivalent of today's
`derivationStrict`: hash the inputs, compute the output paths, write
the `.drv`. v3's `primDerivation` does the attrset walk and constructs
the descriptor, then calls this. The outer `builtins.derivation`
wrapper (already pure-v3) builds the result attrset.

### G. Closure callback ABI  (3 entries + 2 types)

The boundary in the *other* direction: store ops that take Nix
functions need to call back into v3.

```c++
struct ClosureHandle;  // opaque; v3-allocated; trivially copyable

template <typename T> struct EvalResult {
    std::variant<T, EvalError> r;
};

EvalResult<v3::Value> applyClosure(ClosureHandle, std::span<v3::Value> args);

// Function pointer type the store can hold.  Closure-bound at construction.
using FilterCallback = std::function<EvalResult<v3::Value>(std::span<v3::Value>)>;
```

Three rules:

- **Re-entrancy** is bounded by v3's frame stack, not pthread stack.
  `applyClosure` enters v3's dispatch loop on the same C stack frame
  by trampoline (or with an explicit depth limit, like today's
  `BRIDGE1_DEPTH` but enforced inside v3, not the bridge). Goal: no
  matter how deep the closure recursion, store-side C++ stack depth
  stays O(1).
- **Errors** propagate via `EvalResult`, not C++ exceptions across
  the boundary. The store decides whether to abort (most fetchers
  do) or to continue (e.g., `filterSource` skips a path on filter
  error if user asked).
- **Lifetime**: `ClosureHandle` is valid until the v3 evaluator that
  produced it is destroyed. The store must not retain handles past
  evaluation end.

### H. Settings  (1 entry + a struct)

One read-mostly snapshot, taken at evaluator construction. Avoids
threading flags through every primop.

```c++
struct EvaluatorSettings {
    std::string  storeUri;
    bool         pureEval;
    bool         restrictedEval;
    bool         readOnlyMode;
    std::vector<SearchPathItem> nixPath;
    std::set<std::string> allowedUris;
    std::string  currentSystem;
    bool         enableNativeCode;     // gates importNative, exec
    // … a small finite list, stable across an eval
};

const EvaluatorSettings & settings(Evaluator &);
```

`pureEval` and `restrictedEval` are enforced at primop dispatch
inside v3 (see "Sandbox" below); the store doesn't re-check.

### I. Logger / diagnostics  (5 entries + 2 types)

Activity is the only stateful observer pattern that crosses. The
store emits build/copy progress; the CLI consumes.

```c++
struct Activity;
enum class ActivityType { copyPath, downloadFile, build, … };

Activity startActivity(ActivityType, std::string label, ParentActivity);
void     stopActivity (Activity);
void     logMessage   (Verbosity, std::string_view);
void     setProgress  (Activity, uint64_t done, uint64_t expected);
ParentActivity rootActivity();
```

### J. NIX_PATH / findFile  (2 entries)

`findFile` (`<nixpkgs>` resolution) recurses into fetchers when an
entry is a URL; needs its own small interface above raw fetchers.

```c++
SourcePath findFile(const std::vector<SearchPathItem> & path,
                    std::string_view lookupKey);
SourcePath findFile1(SearchPathItem entry, std::string_view subpath);
```

### K. Flake support  (4 entries — separate library, optional)

If `libnixflake` is linked, v3's `builtins.getFlake` and friends
forward to:

```c++
LockedFlake lockFlake(FlakeRef, LockFlags);
LockedFlake readLockedFlake(SourcePath);
v3::Value   callFlakeOutputs(const LockedFlake &, Evaluator &);
FlakeRef    parseFlakeRef(std::string_view);
```

`callFlakeOutputs` returns a v3 Value (the `outputs` attrset), which
is then in v3's hands.

### L. Eval / fetch caches  (4 entries — optional optimisation)

```c++
std::optional<v3::SerializedValue>
        lookupEvalCache (CacheKey);
void    storeEvalCache  (CacheKey, v3::SerializedValue);
std::optional<FetchResult>
        lookupFetchCache(URL, std::optional<Hash>);
void    storeFetchCache (URL, FetchResult);
```

Optional: a v3 build that doesn't link these still works; it just
does no caching across invocations.

## Cross-cutting concerns

### String contexts

Nix strings carry **context**: a set of references to derivations
and their outputs. `derivationStrict` reads it (to compute input
hashes), `unsafeDiscardStringContext` strips it, etc.

The cross-boundary representation:

```c++
// Mirrors src/libexpr/include/nix/expr/value/context.hh:35-94 (the
// authoritative shape).  3-way variant: `DrvDeep` (any output of a
// derivation) is ORTHOGONAL to `Built` (a specific named output) --
// they're not collapsible into one kind+optional<outputName>.
//
// 06b A4: original sketch used {Opaque, DrvDeep, Output} with
// optional outputName.  The actual type uses `Built` (non-optional
// outputName) and keeps DrvDeep separate.  Conflating them loses
// "any output" semantics.
struct ContextElem {
    struct Opaque  { StorePath path;     };
    struct DrvDeep { StorePath drvPath;  };               // all outputs of drv
    struct Built   { StorePath drvPath; std::string outputName; };
    std::variant<Opaque, DrvDeep, Built> data;
};
using Context = std::set<ContextElem>;
```

Every string crossing the FFI is `(string_view, Context)`. v3 keeps
its side-table internally; at the boundary it materializes as the
explicit pair. No information loss.

The store *consumes* contexts but does not produce them — except
indirectly: `addToStore` returns a `StorePath`, and primops that
wrap it (`builtins.path`, derivation outputs) attach a fresh
context.

### Position threading through errors

Every FFI call accepts an optional `PosIdx callerPos`. On error, the
returned `EvalError` carries it. v3 attaches its current call-site
position before invoking; if the store throws, the trace shows where
in `.nix` the call originated.

```c++
struct EvalError {
    std::string msg;
    std::vector<TraceFrame> trace;     // each has PosIdx
};

template <typename T> using Fallible = std::variant<T, EvalError>;

Fallible<StorePath> addToStoreAt(PosIdx caller, std::string name, …);
```

This is a discipline, not a single function — every FFI entry
returns `Fallible<T>` and every entry takes a `PosIdx`.

### Memory management

**Choice point.** Today v3 shares Boehm GC with TW. Two paths:

1. **Keep Boehm.** Boundary values are GC-roots automatically.
   `libnixstore` already uses Boehm. Lowest friction; same
   pause-time / fragmentation profile we have today.
2. **v3 arena, store separate.** Explicit ownership at boundary:
   primitives by value, strings copied at crossing, attrsets/lists
   marshalled into a stable wire form for the store. No GC pauses
   inside v3's hot path; predictable allocation; harder to write the
   FFI.

**Recommendation:** keep Boehm during the transition; design the
FFI so signatures *would* survive a switch (no implicit lifetime
extension; values that cross are either copied or come with
explicit ownership). The doc above already does this — note the
absence of "raw v3 pointers" in store signatures; everything is
either by-value or `StorePath`/`Hash`/etc.

### Re-entrancy and bridge depth

The current `NIX_V3_BRIDGE1_DEPTH=8` exists because each TW→v3 hop
costs a pthread frame. Under the new ABI:

- `applyClosure` does not push a C++ frame per call. It either
  reuses the calling frame (trampoline) or runs in a dedicated
  fiber. v3's frame stack — already a heap structure — handles the
  recursion.
- The depth limit becomes a v3-internal concern: refuse to start
  evaluating if v3 frame stack exceeds N. Configurable, but no
  longer about pthread budget.

### Sandbox / pure-eval gating

Enforced at primop dispatch inside v3, not at each call site. The
primop registry tags each primop:

```c++
struct PrimOpDescriptor {
    std::string name;
    int arity;
    PrimOpFn fn;
    PrimOpFlags flags;   // RequiresImpurity, RequiresFilesystem,
                          //  RequiresNetwork, RequiresStore
};
```

At dispatch, v3 checks the flags against `EvaluatorSettings`. A
single chokepoint, instead of `if (settings.pureEval) throw …` in
each impure primop. The store FFI is unaware.

This is the **complete contract** between v3 and the rest of Nix.
No `EvalState`, no `Expr* eval(env)`, no `forceValue` callbacks, no
`callFunction`, no `__v3_call_bridge_1`, no `tryBridgeAttrLookup`.

## Migration path

The current bridge is a superset of this FFI plus a lot of
historical glue. Path to convergence:

1. **Sketch the header pack** as `include/nix/v3-ffi/*.hh` based on
   §A–L above. Compiling it should produce a stable contract even if
   nothing implements it yet. *Half a day.*
2. **Define `StoreOps`, `Logger`, `PosTable` as interfaces today**,
   with the existing TW-side code as the only implementation.
   v3 stops touching `EvalState` directly; goes through the
   interface. No behavior change. *2–3 days.*
3. **Port the `Tag::Bridge` thunk reads** to the closure-callback
   ABI. Each `tryBridgeAttrLookup` / `__v3_force_attr` call site
   either stays (if the value really comes from outside v3) or is
   eliminated by shapes (S1 from prior review). *1–2 weeks paired
   with shapes.*
4. **Move derivation construction** behind
   `instantiateDerivation`. v3 already builds most of the
   descriptor; finalise the record. *3–5 days.*
5. **Lift the closure-result refusal.** Once the closure-callback
   ABI is the canonical way for outside code to invoke v3 functions,
   v3 can return `Tag::Closure` freely; consumers know how to apply
   it. Deletes `willReturnClosure`, the top-level `Attrs/List`
   short-circuit, and the bulk of `v3_hook.cc`. *1 week.*
6. **Remove the `libnixexpr` dependency from `libnixexprv3`.** Link
   only against `libnixstore` and the parser library. The
   tree-walker becomes either an alternate evaluator (under a flag)
   or is deleted outright. *Cleanup pass.*

After step 6, the diagram from the prior conversation becomes real:

```
nix CLI
   │
   ├── libnixstore         (FFI target)
   ├── libnixexpr-parser   (shared frontend)
   └── libnixexprv3        (sole evaluator)
```

## Risks and unknowns

- **Eval cache compatibility.** TW's existing eval cache stores
  serialized TW Values. If the on-disk format isn't shared, switching
  evaluators invalidates the cache for every flake on disk. Either
  define a v3-native serialization (preferred) and accept the
  one-time cost, or keep the TW format and have v3 read/write it.
- **Boehm interaction with arena.** If v3 ever moves off Boehm, the
  closure-callback ABI must already be lifetime-explicit. Worth
  reviewing each callback signature for accidental dangling-pointer
  assumptions.
- **Performance of the discipline.** Returning `Fallible<T>` from
  every FFI call costs a tagged-union construction and check. On
  store ops (which are slow anyway) this is invisible. On `readFile`
  / `pathExists` (which hot loops use a lot) it might add
  measurable overhead — measure before standardising.
- **Plugin primops.** Today nix supports loadable primop plugins
  (via `--plugin-files`). They're written against `EvalState` /
  `Value`. Going pure-v3 either deprecates them or defines a v3
  plugin ABI (essentially: a way to register a `PrimOpDescriptor`
  and use the closure callback ABI for higher-order arguments).
  Decide this before announcing the FFI as stable.
- **Trace fidelity.** Threading `PosIdx` through every call doesn't
  guarantee good error traces — the store also emits its own trace
  context (which derivation, which output). The error type may need
  a richer structure than the sketch above (`std::vector<TraceFrame>`
  with mixed v3 and store frames).

These are real gaps, not blockers. They become decidable once steps
1–2 of the migration land and we can see how the discipline behaves
under real workloads.
