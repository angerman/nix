## What landed

`src/libexpr-v3/bench/m5-cron.sh` — drift-detection script for the strategic-workload measurement. Three modes:
- `--quick` — 1 warm run (~30 s)
- `--full` — cold + warm + warm-with-drvHashCacheDisk (~2 min)
- `--check-regression N` — fail with exit 1 if delta vs prior entry of same mode exceeds N% wall

Output: append-only TSV ledger at `bench/samples/m5-cron-ledger.tsv` with per-line `timestamp \t git_hash \t mode \t wall_s \t peak_rss_mb \t output_drvPath`. Each entry is fully reproducible: `git checkout HASH -- src/libexpr-v3/` + rebuild + rerun.

## Why this matters

`CARDANO_NODE_M5_2026-05-21.md`'s "919 MB capability claim" was not reproducible from its named commit. The 2026-05-26 evening session spent ~30 minutes confirming the baseline was wrong-at-source via same-host bisect. The cron prevents future drift drama by keeping the baseline LIVE: any "wall regressed" claim has a ledger to cross-check against.

Per `[[same-host-bisect]]` + `[[head-5-counter-trap]]`: cheap measurements precede expensive investigations. The ledger codifies that pattern for the strategic workload.

## Smoke test (this commit)

Two `--quick` invocations + regression check:
```
warm     prev=27.818  now=27.836  delta=+0.1%   ok
```

`--check-regression 20` exits 0 when delta < 20%. Falsifier check: a real wall regression > 20% would exit 1 with explicit `REGRESSION` marker.

## Operational integration

The script is host-agnostic but designed for the dev machine (cardano-node checkout at `/Users/angerman/Projects/iohk/cardano-node`, darwin time format). Wiring options:
- **Daily**: cron entry `0 7 * * * cd /path/to/nix && bench/m5-cron.sh --full --check-regression 15 || mail -s 'M5 drift' ...`
- **Pre-commit hook**: `--quick --check-regression 15` on the v3 development branches
- **Manual**: run after every major v3 change as a sanity check

Currently the script is opt-in (no auto-wiring to all-v3-tests.sh because M5 measurement takes 30 s+ and requires the cardano-node checkout).

## What this DOES NOT do

- Does NOT replace a quiescent-host benchmark runner. Per `[[same-host-bisect]]` + load-avg sensitivity (yesterday's 6-8 load avg invalidated measurements), the ledger is informative-not-authoritative; a `REGRESSION` marker is a starting point for investigation, not a final verdict.
- Does NOT measure pure-compute primops (those are the next deliverable; see `M5_PRIMOP_PROFILE_2026-05-27.md`).
- Does NOT alert on absolute thresholds (e.g., "wall > 40 s"). Only relative-to-prior comparison. Absolute thresholds need calibration vs known-good runs first.
