## 1. Catalog by category

### 1.1 TW → v3 callbacks (the bridge primops)

#### BP1 — `primV3CallBridge1` (`__v3_call_bridge_1`)

* **File:line:** `primops.cc:4541-4917`
* **Registered:** TW-side primop, arity 2 (handle:Int, arg:Value)
* **Function:** TW calls back into v3 to force a previously-bridged Closure with a TW-allocated argument.
* **Args marshalled IN:** `handle` (int, cheap), `arg` (Value — marshalled via `treeWalkerToV3` at primops.cc:4797). The `arg` becomes a v3 Bridge thunk pointing at the TW `nix::Value *`.
* **Result marshalled OUT:** result value from `callClosure` → marshalled via `v3ToTreeWalker` at primops.cc:4908. Often produces a fresh bridge entry (closure return path).
* **Retention:** each call MAY push 1+ new entries into `v3BridgeClosures()` if the result is a Tag::Closure that needs to be bridged back to TW.
* **Hot path:** M5 (20034 calls). Per-call cost includes:
  - depth-guard checks (cheap)
  - bridge-table lookup at handle (cheap)
  - blackhole/cycle detection (cheap)
  - VMState setup + `callClosure` (real eval work)
  - `treeWalkerToV3(arg)` marshalling
  - Potentially `v3ToTreeWalker(result)` round-trip
* **Marshalling minimality:** the `arg` round-trip is unavoidable (TW Value → v3 must wrap somehow). BUT: the RESULT round-trip is the over-marshalling concern. If `callClosure` returns a v3 Closure that immediately gets bridged via `v3ToTreeWalker`, the bridge table gains a new entry retaining the result subgraph. For 20034 calls on M5, that's 20034 potential new entries (actual ≈ 10047 after dedup-by-caching).
* **What's retained that doesn't need to be:** for each BP1 call where TW only needs ONE field of the result, the FULL transitive subgraph is bridged. This is the O3 over-marshalling pattern per inventory §3.3.

#### BP2 — `primV3ForceAttr` (`__v3_force_attr`)

* **File:line:** `primops.cc:4925-5178`
* **Registered:** TW-side primop, arity 2 (handle:Int, attrName:String)
* **Function:** TW forces a single named attr of a bridged Tag::Attrs.
* **Args marshalled IN:** `handle` (int), `attrName` (string — cheap, just a name).
* **Result marshalled OUT:** the attr's Value, marshalled via `v3ToTreeWalker` at primops.cc:5126. **Phase A2 short-circuit (today):** if the attr value is already a Bridge thunk wrapping a TW pointer, return that pointer directly without going through `v3ToTreeWalker`.
* **Retention:** per-call retains a NEW bridge entry IF the attr value is a v3 Closure/Bindings/ListVec not yet bridged.
* **Hot path:** HNE (51 calls), M5 (84 calls). On hello/firefox/python3: 0.
* **Marshalling minimality:** the Phase A2 fast-path catches the "this is already a TW handle" case for free. The slow path (`v3ToTreeWalker` recursion) is still incurred for v3-NATIVE values bridging up to TW. **Over-marshalling:** if TW only reads ONE field of the returned attr (e.g., `meta.broken or false`), bridging the full attrset is wasted work. Inventory §3.2 names this the callback-driven pattern.
* **What's retained that doesn't need to be:** the result of `v3ToTreeWalker` typically creates a new bridge entry (or a chain of them if it's an attrset of attrsets). On HNE, 51 BP2 calls produce ~20 bridge entries — each retaining a transitive subgraph.

#### BP3 — `primV3ForceListElem` (`__v3_force_list_elem`)

* **Status: RETIRED 2026-06-01 (`8c65e9dde`).** Zero calls on all 5 workloads pre-retirement.
* **What was retired alongside:** the Tag::List → TW lazy-bridge construction at `v3ToTreeWalker::case Tag::List` (was allocating per-element `vIdx` + `vApp` Boehm values for lists > 4). Now always eager-bridges.

## 5. What's retained that doesn't need to be — by category

### 5.1 BP1 result retention (M5 driver)

* Each of 20034 BP1 calls produces a v3 Value result.
* That result is bridged via `v3ToTreeWalker` at `primops.cc:4908` → may push a new entry into `v3BridgeClosures()`.
* TW receives the bridged result and forces it; the FORCING typically reads ONE field (e.g., `pkg.outPath` or `pkg.name`).
* The bridge entry retains the FULL transitive subgraph of the result — even though TW only ever needed one field.
* **Not needed retained: the 22+ unused attrs per result, transitively their subgraphs.**
* Mechanism to fix: lazy bridge of the result.  Mark the result as a TW Bridge thunk that's resolved on first force; not pushed eagerly.

### 5.2 BP2 result retention (HNE driver)

* Each of 51 BP2 calls returns an attr value.
* Phase A2 short-circuits the case where the attr is already a Bridge thunk (no new entry).
* For attr values that are v3-NATIVE (Closure, Attrs, ListVec), full transitive bridging occurs.
* TW receives the bridged Value and typically calls one method on it.
* **Not needed retained: the rest of the attr value's subgraph that TW never touches.**
* Mechanism: similar lazy result marshalling.

### 5.3 Duplicate entries (M5)

* Inventory §5 D1: `v3ToTreeWalker` doesn't dedupe.  Same v3 Bindings*/Closure* bridged twice produces two distinct handles.
* On M5: 20034 BP1 calls produce 10047 unique closures (per the bridge-table count of 10047 closures).  ~50% are duplicates per `v3BridgeUniquePtrCounts` (diagnostic at primops.cc:4369).
* **Not needed retained: ~5000 duplicate bridge entries on M5.**
* Mechanism: D1 dedupe (1-2 day work).

### 5.4 Empty bridge-lists table

* Post Phase A1, `v3BridgeLists()` is structurally empty (no push site).
* The table infrastructure (sweep, walk, stats reporting) still iterates an empty vector.
* **Not needed retained: 0 bytes today (table is empty), but the iteration cost + bookkeeping persists.**
* Mechanism: delete table accessor + iteration sites.  Code hygiene.

### 5.5 vName + vApp per-attr TW Values (Inventory §3.3 O3)

* When v3 bridges a >4-entry attrset to TW, the code at `primops.cc:5572-5594` allocates ONE `vName` + ONE `vApp` TW Value per attrset entry.
* For a 28-entry attrset: 58 TW Values created eagerly.
* TW typically reads 3-5 entries on hello.drvPath drv attrsets — 23 + Values are dead-on-arrival.
* **Not needed retained: 80-90% of the per-attr TW Values.**  ~10K-100K wasted TW Boehm allocs per workload (inventory's O3 estimate; unmeasured).
* Mechanism: shared lazy primop taking (name, index) — eliminates per-entry vName.  Architectural; 1 wk.

### 5.6 Cycle-guard maps in BP1 (per-call cost)

* `tlsForceAttrInProgress` / `tlsForceAttrInProgressVm` / `bridgePrimopDepth` are thread-local maps used for cycle detection in BP2.  Similar for BP1.
* On M5 with 20034 BP1 calls these maps are entered/exited that many times.  Each insert/erase is O(log) or O(1) amortized.
* **Not needed retained beyond the call:** the maps are cleared on guard destruction; they don't retain.
* Mechanism: structurally minimal already.

## 6. What's NOT bridges (but lives nearby)

For completeness, items the user might confuse with FFI but aren't:

* **fakeClo pool** (`alloc.hh:Alloc::allocFakeClo`) — internal v3 mechanism for closure recycling; no TW crossing.
* **ImportCache** (`primops.cc:8103-8115`) — keyed by absolute path, stores CompilationUnits + cached `Value` results.  No bridge entries.
* **disk_cache** — SQLite-backed bytecode cache.  Pure libsqlite3 use; no TW.
* **Boehm GC** itself — `GC_add_roots` calls register ARENA pages for Boehm scan.  Not a bridge.
* **`stringContextSideTable`** — v3-side store-context tracking.  Not a bridge.
* **Bridge-root registry** (`bridge_root_registry.cc`) — side-table tracking Boehm roots for bridged values.  Infrastructure, not a bridge primop.

## 8. Honest limits

* **Cross-architecture testing not done.** All measurements are aarch64-darwin.  If a linux/x86_64 cross-build hits a `derivationStrict` shape my native path doesn't handle, `V3_DRV_KEEP_BRIDGE=1` is the escape hatch.
* **CA + structuredAttrs + impure drv shapes not explicitly exercised.** On natural workloads they didn't fire either.  The native impl's coverage is empirically real but might miss synthetic adversarial cases.
* **M5 BP1's 20034 calls drives a wall regression** vs other workloads.  This is a real eval-time cost (not just memory).  Reducing M5 BP1 frequency would help BOTH wall and RSS.
* **The 99.8% retention figure from `BRIDGES_HOLD_RETENTION_2026-05-29` is end-of-eval, not peak.**  Peak retention is different (the working set during eval, not at the end).  Per `GC_AND_MEMORY_ACCOUNTING_AUDIT §4.1`, peak_rss = ru_maxrss is monotonic; retention reductions help current RSS but not peak.
* **Marshalling minimality verdicts in §2 are based on call-pattern inspection, not exhaustive code review.** O-3 and O-4 estimates are from inventory §3.3/3.4 + my reading; need measurement to bound effort vs yield.
* **D1 dedupe yield is a projection (50% M5 entry reduction).** Needs implementation + measurement to confirm.
