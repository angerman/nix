# v3 FFI Surface — Adjustments after critical review (2026-05-06b)

Companion to `FFI_PLAN_2026-05-06.md`. Four parallel agents reviewed the
plan against the actual code and against the literature on embedded-VM
FFIs (Lua, V8, JNI, OCaml, CPython, wasm-component, .NET hosting,
Erlang NIFs, Tcl, GraalVM). This document records the corrections that
survive critical review. Several agent claims were rejected; those are
noted at the end.

Confidence tags as before: **C** verified against code, **L** likely,
**S** speculative.

---

## Adjustments to keep

### A1. Add `EvalScope` (RAII handle lifetime) — **highest priority**

The single biggest gap. The literature is unanimous:

- V8: `HandleScope` + `Local<T>` + `Persistent<T>`
- OCaml: `CAMLparam`/`CAMLlocal`/`CAMLreturn`
- wasm component model: `own<T>` vs `borrow<T>`
- JNI: local refs vs global refs

CPython's exposure of `Py_INCREF`/`Py_DECREF` to the host is
universally regretted. The current plan exposes `ClosureHandle` with
no scope discipline — which leaves lifetime as the host's problem and
re-derives CPython's bugs.

**Adjust:** add a scope type to category G.

```c++
struct EvalScope {              // RAII
    EvalScope(Evaluator &);
    ~EvalScope();               // invalidates all handles created within
    EvalScope(const EvalScope &) = delete;
};

struct ClosureHandle    { … };  // valid only within enclosing EvalScope
struct GlobalClosureHandle { … };  // outlives scope; explicitly released

GlobalClosureHandle promoteToGlobal(ClosureHandle);
void                releaseGlobal  (GlobalClosureHandle);
```

The store keeps `GlobalClosureHandle` for callbacks that survive a
single FFI call (e.g., a `PathFilter` used during a long
`copyPathToStore`). Everything else uses `ClosureHandle` and the scope
guarantees cleanup. (C from literature; L for Nix specifics.)

### A2. Fibers, not trampoline — match the existing code

`bridge_yield.cc:40–93` already implements ucontext-based fibers
(`runInFiber`, mailbox protocol, `activeFiberDriverDepth`). The plan
claimed "trampolined" re-entry; the code is fiber-based and has been
for some time.

**Adjust §G text:** strike the trampoline claim. Replace with:

> Re-entrancy: `applyClosure` runs on a pre-allocated fiber stack
> (`bridge_yield.cc`); the C stack stays at O(1) regardless of closure
> recursion depth. Per-platform caveats: `fiber.cc` notes a macOS
> arm64 limitation. The depth limit (today's `BRIDGE1_DEPTH=8`) moves
> inside v3 and becomes a fiber-scheduling concern, not a pthread-
> stack budget.

(C — verified at `bridge_yield.cc:40–93`.)

### A3. Expand `DerivationDescriptor`

Agent 2 enumerated 10 missing fields with file citations against
`derivation-options.hh:43–175` and `derivationStrictInternal`
(`primops.cc:1612–2005`):

```c++
struct DerivationDescriptor {
    // … existing fields …

    // Sandbox / platform
    bool                 noChroot               = false;   // __noChroot
    std::optional<std::string> sandboxProfile;             // __sandboxProfile (darwin)
    bool                 darwinAllowLocalNetworking = false;
    std::set<std::string> impureHostDeps;                  // __impureHostDeps
    std::set<std::string> impureEnvVars;

    // Scheduling
    std::set<std::string> requiredSystemFeatures;
    bool                 preferLocalBuild       = false;
    bool                 allowSubstitutes       = true;

    // Reference graph export
    std::map<std::string, StorePath> exportReferencesGraph;

    // Lowering hint
    bool                 ignoreNulls            = false;   // __ignoreNulls

    // Per-output checks (NESTED, not flat — store wants per-output specificity)
    struct OutputChecks {
        std::optional<std::set<StorePath>> allowedReferences;
        std::optional<std::set<StorePath>> allowedRequisites;
        std::optional<std::set<StorePath>> disallowedReferences;
        std::optional<std::set<StorePath>> disallowedRequisites;
        std::optional<uint64_t> maxSize;
        std::optional<uint64_t> maxClosureSize;
    };
    std::map<std::string /*outputName*/, OutputChecks> outputChecks;
};
```

The nesting is required: `derivation-options.hh:43–87` lets each
output have its own checks. The plan's flat representation drops
information.

(C — `derivation-options.hh:43–175`, `primops.cc:1612–2005`.)

### A4. String context: 4 variants, not 3

The current plan: `{Opaque, DrvDeep, Output}` with `outputName`
optional on the Output kind. The actual type
(`src/libexpr/include/nix/expr/value/context.hh:35–94`) is a 4-way
sum:

```c++
struct ContextElem {
    struct Opaque  { StorePath path; };
    struct DrvDeep { StorePath drvPath; };               // all outputs of drv
    struct Built   { StorePath drvPath; std::string outputName; };
    using Variant = std::variant<Opaque, DrvDeep, Built>;
    Variant data;
};
```

`DrvDeep` and `Built` are orthogonal: `DrvDeep{p}` means "any output of
`p`" while `Built{p, "out"}` means "specifically the `out` output of
`p`". Conflating them loses information. (C —
`src/libexpr/include/nix/expr/value/context.hh:35–94`.)

### A5. `EvalError` richer than the sketch

Today's `EvalError` (`src/libutil/include/nix/util/error.hh`,
`src/libexpr/include/nix/expr/eval-error.hh:114–124`) carries
`exitStatus`, `Suggestions` (typo-fix hints), and a structured trace
with positions and fmt-style hints — not just a formatted string.

Combine Agent 3's correctness concern with Agent 4's literature
recommendation (V8 separates `Message` from `StackTrace`; format is
the host's job):

```c++
struct EvalError {
    std::string  msg;                       // unformatted; HintFmt-style
    PosIdx       primaryPos;
    std::vector<TraceFrame> trace;          // each: PosIdx + hint
    unsigned     exitStatus = 1;
    std::vector<Suggestion> suggestions;    // typo-fix hints
};
```

The host renders. v3 supplies positions and unformatted message text.
Width / colour / terminal-vs-JSON is the renderer's concern.
(C from `eval-error.hh`; L for shape; L from V8 literature.)

### A6. Position threading: lookup helper, not pure parameter

The plan said "every FFI call accepts `PosIdx caller`." Realistic
mechanism is harder: `CallFrame` (`vm.hh:43–60`) has no position
field; v3 reconstructs positions from `(bytecodeIp, side-table)`.
Threading `PosIdx` on every call site means either:

- per-instruction write to `VMState::currentPosIdx` (per-instruction
  cost), or
- a lookup helper called only at FFI-crossing points:

```c++
PosIdx currentPos(const VMState &);   // O(log N) side-table lookup
```

**Adjust:** keep the `PosIdx caller` parameter convention in the FFI
signatures (it documents intent and lets primops pass an explicit
override), but the *implementation* in v3 calls
`currentPos(vm)` at the boundary rather than maintaining a
hot-path field. (C — `vm.hh:43–60`, `vm.cc:884–914`.)

### A7. `Fallible<T>` at the boundary only

The plan implied `Fallible<T>` everywhere. The codebase throws C++
exceptions at hundreds of sites (`primops.cc` lines 230, 322, 330,
347, 473, 581, 594, 651, 770, 1047, 1147, 1191, 1246, …). Wholesale
rewriting is unrealistic and would cost ABI clarity for no
correctness gain.

**Adjust:** `Fallible<T>` is enforced *only* at the FFI boundary —
the function declared in the v3-FFI header. Internally v3 may throw;
the FFI shim catches at the crossing and constructs the variant.
Symmetrically, errors *returned* into the FFI by the host are
re-thrown inside v3.

This matches Lua's `lua_pcall` (one protected boundary, internal
unwinding stays unwind-based) and avoids GraalVM's "every boundary is
typed" overhead. (Synthesis of Agent 3 and Agent 4.)

### A8. Parser extraction: future cleanup, not a precondition

`Expr` is defined in `libnixexpr` (`src/libexpr/include/nix/expr/nixexpr.hh:99`),
with ~20 subclasses and an `eval(Env&)` method per class. The plan
spoke of a `libnixexpr-parser` shared library as if it existed;
extracting it requires carving the AST hierarchy out of the
tree-walker.

**Adjust the diagram and migration path:** treat the parser as
"currently part of `libnixexpr`, extracted later." v3 lowers from
opaque `Expr*` (it doesn't need to know the subclasses; it walks via
the existing visitor). Extraction becomes a step *after* the bridge
shrinks. (C — `nixexpr.hh:99` and the eval-method-per-Expr pattern.)

### A9. Plugin ABI: pick one before announcing the FFI as stable

Two viable answers, plan must commit:

- **Option A — Hard cut.** v3 plugins are written against a v3 C ABI:
  ```c++
  extern "C" void nix_plugin_v3(v3::PrimOpRegistry &);
  ```
  Old `RegisterPrimOp` plugins are deprecated. Cleanest, but breaks
  every existing plugin.

- **Option B — Compat shim.** Old plugins keep working through a
  Value-bridge: `RegisterPrimOp` is intercepted; the v3 registry
  wraps each old primop in a closure that marshals v3 Values to/from
  TW Values. Slow path, but no compatibility break.

**Recommendation:** Option B during the transition, Option A after a
deprecation window. (S — depends on user base; needs a call.)

### A10. Latency class on FFI calls

From the Erlang NIF/Port lesson (Agent 4): some FFI calls are
"NIF-class" (must return fast — `applyClosure`, `forceValue`, symbol
lookup) and others are "Port-class" (potentially slow —
`fetchurl`, `addToStore`, `realiseDerivation`). Tag them in the type
system:

```c++
template <typename T> struct BlockingFFI : Fallible<T> { … };

BlockingFFI<FetchResult> fetchurl(URL, …);          // Port-class
Fallible<StorePath>      parseStorePath(string_view); // NIF-class
```

The wrapper does nothing semantically but documents the latency class
and lets future scheduling/profiling hook in. Cheap; surfaces a real
distinction that today is implicit. (Agent 4 synthesis; useful.)

### A11. Eval cache: commit to v3-native serialization

The plan listed cache compatibility as a "risk and unknown." Commit:
v3 owns its serialization format (already partly in `serialize.cc`);
existing TW eval-caches invalidate on first v3 run. One-time cost,
worth it for clean separation. (Agent 1 + agent 2 — both agree this
should be decided, not deferred.)

### A12. Missing surface in category E (Store ops)

Agent 1 noted three real gaps against `src/libstore/include/nix/store/store-api.hh`:

- `addMultipleToStore` (batched, used by hot paths)
- `computeFSClosure(StorePath, callback)` (transitive references)
- A `PathFilter` callback type (used by `addToStore` overloads)

Add to category E. Count goes 10 → 13.

### A13. Sandbox gating needs a `flags` field on `PrimOp`

`primop.hh:203–216` has no flags field today. Adding one is a
concrete piece of implementation work, ~1–2 days, must precede the
sandbox-at-dispatch design. Note in the migration path explicitly.

## Agent claims rejected

These came up in review but don't survive scrutiny:

- **"Filter callback returns `bool`, not `Value`."** (Agent 2.) The
  Nix-language closure returns a `Value` (the result of `path: type:
  body`); the v3-side adapter calls `forceBool` to extract. The FFI
  signature `EvalResult<Value> applyClosure(...)` is correct as-is.
  The agent confused the language-level return type with the
  C++-level callback return.

- **"Reframe goal as 'minimal FFI layer over EvalState' rather than
  'v3 independence'."** (Agent 1.) Overstated. The plan is for the
  *future* state. The agent's data correctly shows v3 *currently*
  uses `EvalState` heavily — that's the migration starting point, not
  the goal. The migration path already says "v3 stops touching
  `EvalState` directly; goes through the interface." Keep the
  goal; refine the migration steps.

- **"GraalVM polyglot model deserves consideration."** (Implicit in
  literature review.) Reviewed and rejected by Agent 4 itself. Nix
  has one language; the polyglot overhead is unjustified. Confirmed
  reject.

- **".NET delegate-as-function-pointer for closures."** (Implicit in
  literature.) Doesn't fit Nix because closures capture environments;
  function pointers can't. The handle-based ABI in the plan is
  correct.

## Migration path: revised step ordering

Original plan had 6 steps. Reorder for the corrections:

1. **Sketch the header pack** (now ~59 functions, ~20 types).
   *Half a day.*
2. **Add `EvalScope`** — RAII type, all handle-returning FFI
   functions take a scope reference. Touches v3 internals minimally;
   establishes lifetime discipline before anyone depends on
   handle-leaking semantics. *2–3 days.*
3. **Add `flags` to `PrimOp`** — implement sandbox-at-dispatch.
   *1–2 days.*
4. **`Logger`, `PosTable`, `Settings` interfaces** — replace direct
   `EvalState` access in v3 with these. No behaviour change.
   *2–3 days.*
5. **Define `Fallible<T>`, `EvalError`, `BlockingFFI<T>` at
   boundary** — wrap existing exception sites at the FFI shim.
   *2 days.*
6. **`DerivationDescriptor` finalisation** — add the 10 missing
   fields and the nested `OutputChecks`. *3–5 days.*
7. **`tryBridgeAttrLookup` etc. → closure-callback ABI.** Pair with
   shapes work (S1 from prior reviews) since they share the same
   "v3 owns the value" precondition. *1–2 weeks paired.*
8. **Lift the closure-result refusal.** Deletes `willReturnClosure`
   etc. *1 week.*
9. **Plugin ABI decision and implementation** — Option B compat
   shim. *1 week.*
10. **Parser extraction** — carve `Expr` and the parser out of
    `libnixexpr`. *2–4 weeks; deferable.*
11. **Drop `libnixexpr` link-time dependency.** Cleanup pass.

Steps 2, 3, 4 in the new order are independent and can run in
parallel. They establish the discipline that everything after assumes.
Step 10 (parser extraction) was implicit in the original plan; it
becomes its own milestone here because Agent 1 correctly noted the
real cost.

## Risks revised

The plan's risk list survives mostly intact, with two updates:

- **"Plugin primops" risk graduates to a concrete decision** (A9).
  Pick Option B; plan accordingly.
- **"Trace fidelity" risk reduces** (A5). Splitting `EvalError` into
  unformatted+structured form (à la V8) gives the host control of
  rendering. The risk was the result of under-specifying `EvalError`,
  not a deep architectural problem.
- **New: fiber-platform fragility.** `fiber.cc:20` notes a macOS
  arm64 limitation. Worth understanding before committing the
  fiber-based re-entrancy story to ABI documentation.

## What survives unchanged from the original plan

- 12 categories (now 13 with `EvalScope` formally separate).
- The opaque-handle pattern (no GC strategy in the ABI). Confirmed
  by every embedded-VM design surveyed.
- String contexts at the boundary as `(string_view, Context)`.
  Variant enumeration was wrong (now 4 not 3); the *approach* is
  correct.
- Settings as a snapshot, not threaded per-call.
- `Logger` / activity as a stateful observer.
- Migration target: `libnixexprv3 → libnixstore + parser`, no
  `libnixexpr` dependency.

The plan was directionally right. The adjustments harden specific
contracts (handle scope, error shape, derivation fields) and align
the implementation claims with the existing code (fibers, not
trampolines; `Fallible<T>` only at boundary; parser extraction is a
separate milestone).
