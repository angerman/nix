# v3 Bytecode VM — Multi-Agent Review

**Date:** 2026-05-03
**Branch:** `angerman/2.35-eval-profiling-v2` @ `cce5dcc51`
**Scope:** `src/libexpr-v3/` (the actual v3 VM, ~16.9k LoC) + the v3 hooks installed
in `src/libexpr/`. The pre-existing tree-walker / v2 bytecode VM in `src/libexpr/`
is referenced for parity comparisons but not the subject.

**Method.** Six review agents ran in two waves. Wave 1: research on lazy abstract
machines, then four parallel reviewers (runtime, compiler, GC, bridge). Wave 2:
two adversarial critics that re-verified each finding against the code,
re-rated severity, flagged false positives, and surfaced what the first wave
missed. After verdict triage there are **78 findings**, of which the critics
escalated 2 and confirmed-but-lowered 8. No outright false positives.

---

## 1. Executive summary

The v3 VM is a thoughtful clean-room replacement: single bytecode pipeline,
16-byte tagged Values, FAM closures, re-entrant dispatcher, fiber bridge.
The lineage is recognisably STG-flavoured (update-on-return, blackholing for
cycle detection) with eval/apply calling — appropriate for a dynamically typed
target. Where it diverges from STG it usually documents why (WC-37/38 plans,
USAGE.md, OPTIMIZATION_PLAN.md). 142/142 lang tests pass and benchmarks show
real speedups on attrset-heavy code.

The review surfaces **two systemic problems**, **a handful of correctness
defects**, and a substantial body of dead Phase-N scaffolding.

The systemic problems:
- **GC blind spots from non-arena, non-Boehm storage.** `vm.valueStack` /
  `vm.withStack` are plain `std::vector<Value>`; `ValuePair`s are `std::malloc`'d;
  bridge tables are `static std::vector<Value>`; bridge string buffers are
  `std::malloc`'d; arena `kHugeCutoff` fallback is `std::malloc`'d. Boehm sees
  none of these as roots, and reachability holds only via the conservative
  C-stack scan. Any GC trigger between "Value leaves the C stack" and "Value
  reaches a registered root" can lose the object. Today the system works
  largely by accident.
- **Eager forces at emit time.** The lowerer wraps ~22 sites in `forceVal`,
  which (a) defeats lazy semantics in the way WC-38 has been chasing, (b) blocks
  the tail-call peephole on the `then` branch of `if`, and (c) multiplies
  suspended-thunk fires on the hot path. Tree-walker forces on consume; v3
  forces on produce.

The discrete correctness defects worth fixing first:
1. **`OP_REC_BINDING_SLOT_REF` SymbolId not remapped on disk-cache load**
   (ID-C2) — silent miscompilation of every cached CU using `with rec`.
2. **`ValuePair` std::malloc'd, `valueStack` std::allocator'd** (ID-G12 / ID-G13)
   — latent GC corruption.
3. **`primTryEval` catches all `std::exception`** (ID-R2) — direct semantic
   divergence from tree-walker, observable, likely explains some silent
   fail-test passes.
4. **`OP_TAIL_CALL` keeps the outer frame's with-stack base** (ID-R1) — leaks
   `with` bindings into a tail-callee's lookup scope, real lexical-scoping bug.
5. **`inherit (e) x y` re-lowers `e` per name** (ID-C1) — side-effecting `e`
   fires N times instead of once.
6. **`treeWalkerToV3` drops nFunction to mkNull** (ID-B6) — round-trip identity
   loss across nested bridges.

Everything else is dead scaffolding (Phase-3 `OP_LOAD_SLOT_REF`,
`ir::PosExpr`/`Negate`/`RecAttrSet`, `WithLookup::depth`, `kInvalidFunc`,
`primV3CallBridge2`, `Block::params`, `OP_NOP`, six `NIX_V3_*` env probes), perf
smells, or comment/code drift.

## 2. Background — abstract machines, briefly

The v3 design sits squarely in the STG family (Peyton Jones 1992,
"Implementing lazy functional languages on stock hardware") with eval/apply
calling (Marlow & Peyton Jones 2006). The relevant invariants from that
literature are:

- **Bijection between live update frames and blackholed thunks across exception
  unwind.** WC-37 was a violation of this; the fix unwinds `vm.frames` +
  `vm.valueStack` + `vm.withStack` on catch. The runtime review confirms the
  fix is correct *for thunks*; the bridge review notes apps and recovery
  thunks aren't held to the same invariant.
- **One calling convention, consistently.** v3 is eval/apply throughout, which
  is forced anyway because Nix is dynamically typed. No mixed-convention
  defects found.
- **Per-primop forcing table.** v3 declares `lazyArgs` per primop (good); the
  emit-time forces in lower.cc are mostly redundant overlays on top of that
  (the WC-38 territory).
- **Tail call vs return chain.** WC-38 is exactly Reid's
  "putting the spine back" / Marlow's "asynchronous exceptions in Haskell"
  territory: aggressive return-frame push corrupts updates on unwind. v3 has
  the chain push gated off by default (`NIX_V3_RETURN_CHAIN`).

For a Nix-style runtime where `Value` is a tagged union, GHC's pointer-tagging
trick doesn't apply, but the discipline does: every container-of-Value must
have its discriminant set before the payload is observed by any other code
path, including GC.

## 3. Critical findings

These are correctness or memory-safety hazards. Action recommended now.

### CRIT-1 — `OP_REC_BINDING_SLOT_REF` SymbolId not remapped on disk-cache load
**[ID-C2 — confirmed-RAISE]** — `serialize.cc:99-208`, opcode `bytecode.hh:154`,
emit at `emit.cc:520, 655`.

`remapSymbolsInBytecode` switches on opcode and remaps SymbolIds for
`OP_ATTRS_HAS`, `OP_WITH_LOOKUP`, `OP_ATTRS_SELECT`, `OP_ATTRS_INIT`,
`OP_ATTRS_INIT_DYN`, `OP_ATTRS_REC_INIT`, `OP_ATTRS_REC_SET` — but not
`OP_REC_BINDING_SLOT_REF`, which carries a `[sym:24]` operand. The remap runs
on every disk-cache load (`serialize.cc:430`).

**Impact.** Every cached CU using `with self;` or `lib.fix` rec-attrset slot
references will look up the wrong SymbolId after a process restart with a
different global symbol table layout. Symptoms: blackholes or wrong-attribute
reads in nixpkgs-style flake evaluation after a warm cache hit. Hard to
reproduce on demand because tests probably use cold caches.

**Fix.** Add an `OP_REC_BINDING_SLOT_REF` arm to the remap switch. While there,
audit every opcode in `bytecode.hh` against the switch — same drift could
affect future opcodes.

### CRIT-2 — `vm.valueStack` and `vm.withStack` use `std::allocator`, not Boehm
**[ID-G13 — confirmed-RAISE]** — `include/v3/vm.hh:64`.

`std::vector<Value>` defaults to `std::allocator`, which calls
`::operator new` → libc malloc. The storage is **not** in any registered
Boehm root region. Every Value pushed there holds payloads
(Closure*, Bindings*, Thunk*, ListVec*) that are Boehm-managed, so the only
reachability path is via the conservative C-stack scan picking up local
copies during dispatch.

**Impact.** Latent. A GC trigger after pushing a transient Value onto the
stack and before the next opcode reads it can reclaim the payload. Today the
system works because (a) GC triggers are infrequent in opcode bodies, (b)
arena root regions accidentally cover many payloads, (c) macOS Boehm
heuristics are forgiving. On Linux/aarch64 or under aggressive GC the cracks
will show.

**Fix.** Use `std::vector<Value, traceable_allocator<Value>>` (the project
already uses this idiom for `VMState::frames` in v2). Same fix for
`withStack`.

### CRIT-3 — `ValuePair` std::malloc'd outside the GC
**[ID-G12 — confirmed-RAISE]** — `vm.cc:1140, 3603`; primops.cc:602, 675, 1010,
1014, 2229.

`ValuePair * vp = static_cast<ValuePair *>(std::malloc(sizeof(ValuePair)));`
allocates outside both the v3 arena and Boehm. The pair is stored in
`Value::payload.pair` for App / PrimOpApp values; `vp->left` and `vp->right`
may carry Boehm-managed payloads (Closure, Thunk, Attrs).

**Impact.** Same class as CRIT-2 but worse: ValuePairs are long-lived (they
back App chains constructed by primops like `map`, `genList`, `mapAttrs`).
Boehm doesn't know the ValuePair exists, so the inner Values' payloads can be
reclaimed under load. Crashes will look like random thunk corruption or "type
error: expected closure, got null".

**Fix.** Route ValuePair allocation through `Alloc::*` (which puts it inside a
`GC_add_roots`-registered arena block) or `GC_malloc_atomic` if Boehm
should not scan the inner words (it should). 8+ call sites; centralize via
`Alloc::allocPair`.

### CRIT-4 — Bridge `std::malloc` allocations bypass GC entirely
**[ID-B1 — confirmed-RAISE]** — `primops.cc:235, 602, 675, 1010, 1014, 2229`.

`mkStringValueOwned` and the App/PrimOpApp builders in `primMap`,
`primGenList`, `primMapAttrs` use `std::malloc(...)` directly. This is a
specific instance of the CRIT-3 family but compounded: bridge primops are
the path by which v3 Values cross into the tree-walker, and any GC during
the tree-walker leg can reclaim the inner v3-managed objects through
malloc'd holders.

The critic also flagged a **missed twin**: the bridge tables themselves
(`v3BridgeAttrs`, `v3BridgeLists`, `v3BridgeClosures`) are
`static std::vector<Value>` whose backing array is malloc'd — the *table*
holds Value payloads with GC pointers and is invisible to Boehm.

**Fix.** Same as CRIT-3. Route every bridge-side allocation through `Alloc::*`,
including the table storage.

## 4. High-severity findings

### HIGH-1 — `OP_TAIL_CALL` leaks outer frame's captured-with entries
**[ID-R1 — confirmed-RAISE]** — `vm.cc:1418-1425`.

OP_TAIL_CALL keeps the reused frame's `withStackBase` and pushes the
TC callee's `capturedWiths` *on top of* whatever the outer frame had.
`pushCapturedWiths`'s contract requires the caller to set the new frame's
`withStackBase` to `vm.withStack.size()` first; OP_TAIL_CALL violates it.
`withLookup` walks down to `frames.back().withStackBase`, so a cross-closure
TC callee will see the outer caller's `with` bindings.

**Impact.** Real lexical-scoping bug. Self-recursive TC is unaffected (same
captures), but `f x = g x` where `g` was defined under different `with` chain
will leak names from `f`'s scope into `g`'s lookup.

**Fix.** Truncate `vm.withStack` to `cur.withStackBase` *before* calling
`pushCapturedWiths(vm, tcCallee->capturedWiths)`.

### HIGH-2 — `primTryEval` catches all `std::exception`
**[ID-R2 — confirmed]** — `primops.cc:5267-5290`.

v3: `try { forceValue ... } catch (const std::exception &) { successV = vFalse; }`.
Tree-walker: catches only `AssertionError`. ThrownError derives from
AssertionError so both `assert false` and `throw "..."` are caught by
tree-walker; pure type errors (`1 + "x"` — an EvalError) are not.

**Impact.** `(builtins.tryEval (1 + "x")).success` is `false` in v3 but
throws in tree-walker. User-visible semantic divergence; can mask type
errors users want to see.

**Fix.** Introduce a v3 AssertionError type (or a tag/inheritance hierarchy)
and have `primTryEval` catch only that. OP_ASSERT (`vm.cc:2995`) needs to
throw the new type.

### HIGH-3 — `valueLess` doesn't force lazy list elements
**[ID-R3 — confirmed]** — `vm.cc:228-241`.

The list branch reads `a.payload.list->elems[i]` raw and recurses. If an
element is `Tag::Thunk`, `Tag::App`, or `Tag::Slot`, the recursion hits the
"unsupported operand types" throw. `valueLessHelper` (`primops.cc:5301`)
does the right thing.

**Impact.** After WC-35 (lazy `mapAttrs`/`map` entries via `Tag::App`) any
list passed through `<` could contain App entries. `[(map id [1 2]) [1 3]] < [...]`
will throw spuriously.

**Fix.** Take `VMState &` and call `forceValue(vm, a.payload.list->elems[i])`
before recursing.

### HIGH-4 — `inherit (e) x y` re-lowers `e` per name
**[ID-C1 — confirmed]** — `lower.cc:974-982`.

`lowerInheritFrom` calls `lowerExpr((*fromExprs)[displ])` once per inherited
name. Each AttrDef wraps its own thunk. Tree-walker's `buildInheritFromEnv`
shares one Env cell for all names.

**Impact.** Side-effecting `e` (`builtins.trace`, `import` of an
import-from-derivation file) fires N times under v3 vs once under
tree-walker. Also IR/closure bloat proportional to N.

**Fix.** Lower `e` once into a synthetic shared MkThunk; rewrite each
`inherit (e) name` to `AttrSelect(<that VarId>, name)`.

### HIGH-5 — Bridge `std::malloc` GC bypass
**[duplicate of CRIT-4 — see above]**

### HIGH-6 — Arena blocks `std::malloc`'d but never zeroed
**[ID-G1 — confirmed-RAISE]** — `include/v3/alloc.hh:210-228`.

`Arena::refill()` does `std::malloc(kBlockSize)` then `GC_add_roots(blk, blk + kBlockSize)`
without zeroing. Boehm conservatively scans every word in the registered
region. With 16MB of OS-recycled garbage per block, any pointer-shaped bit
pattern pins the corresponding Boehm-managed object until process exit.

**Impact.** Phantom retention scaling linearly with arena lifetime. On a
long-running flake evaluator (Hydra, lang-server, daemon) this is a real
memory creeper.

**Fix.** `std::calloc(1, kBlockSize)` or `std::memset(blk, 0, kBlockSize)`
before `GC_add_roots`.

## 5. Medium-severity findings

### MED-1 — `treeWalkerToV3` drops nFunction to mkNull
**[ID-B6 — confirmed]** — `primops.cc:2649-2662, 2992-2995`.

Tree-walker `nFunction` → `treeWalkerToV3` returns `mkNull`. The Bridge-thunk
short-circuit only triggers for previously-bridged values. A function created
on the tree-walker side and entering treeWalkerToV3 fresh hits the type
switch and becomes null.

**Impact.** Round-trip identity loss when a function flows v3 → tw → v3
through a non-Bridge path. Breaks `let f = id; in [f f]`-style sharing
across nested bridges.

**Fix.** Wrap nFunction values into a v3 BridgeThunk so the round-trip is
reversible, or at minimum return a Slot/wrapper closure instead of mkNull.

### MED-2 — Tail-call peephole only catches the `else` branch of `if`
**[ID-C16 — confirmed-RAISE]** — `emit.cc:757`.

`if (decodeOp(unit.code.back()) == OP_CALL)` only matches the final
instruction of the elseBlock. The thenBlock's `OP_CALL` is followed by an
`OP_JUMP` past the elseBlock and never gets the rewrite.

**Impact.** Recursive folds typically take the form
`if cond then result else f acc tail` — recursion in the *else* branch, OK.
But `if cond then f x else result` — recursion in the *then* branch — never
gets TCO. Leaks C-stack on common idiom.

**Fix.** Walk back across `OP_JUMP` chains: if the last meaningful
instruction (skipping OP_JUMPs) before OP_RETURN is OP_CALL, rewrite. Better:
mark `App` nodes that are in a return-position context as `tailcall=true` at
IR level so the rewrite composes with `If`/`Assert`/`With`/short-circuit.

### MED-3 — `OP_HALT` ignores `CFF_FORCE_RETRY`
**[ID-R4 — confirmed-LOWER]** — `vm.cc:3112-3116`.

OP_HALT pops `finalResult` and exits without the retry-driving logic that
OP_RETURN's caller-resume runs.

**Impact.** Unreachable in well-formed bytecode today (force+halt always
sandwich body work). Genuine concern: `clearBlackMarksOnException` (line 3140)
doesn't clear `CFF_FORCE_RETRY`, so an exception unwind can leave a frame
with the flag set.

**Fix.** Either chase Tag::Thunk/App/Slot in OP_HALT before `finalResult`,
or unify HALT/RETURN tail-handling. Also add CFF_FORCE_RETRY clear to the
unwind path.

### MED-4 — `withLookup` uses substring match on `e.what()` to detect blackholes
**[ID-R5 — confirmed]** — `vm.cc:373, 393`.

`what.find("blackhole")` is the discriminator between "skip this with-stack
entry" and "rethrow". User code that throws an error containing the literal
"blackhole" silently disappears during with-lookup.

**Fix.** Throw a typed `BlackholeError` and catch that.

### MED-5 — Heavy emit-time forces (the WC-38 territory)
**[ID-C13 — confirmed]** — `lower.cc:740-742, 800, 811, 829, 1336, 1404, 1419` (~22 sites).

Tree-walker forces on consume; v3 forces eagerly at emit. The OPTIMIZATION_PLAN
calls this out. Each redundant force is an extra suspended-thunk fire.

**Fix.** Per the plan, audit each `forceVal` against tree-walker. Most can
be dropped because the consuming opcode already does OP_FORCE.

### MED-6 — `OP_ATTRS_INIT` heap-allocates four std::vectors per call
**[ID-R11 — confirmed]** — `vm.cc:2092-2105`.

Names, poses, values, entries-tuple — four heap allocations per attrset
literal. Runs millions of times in nixpkgs. OP_STR_CONCAT got a `kSmall=8`
SBO; this didn't.

**Fix.** SBO of ~16 entries; heap fallback only when n > kSmall.

### MED-7 — `computeFreeVars` fixed iteration cap (16) without diagnostic
**[ID-C11 — confirmed]** — `ir.cc:281-330`.

Silently exits after 16 iterations regardless of convergence. Pathological
mutual recursion produces wrong upvalue lists → silent miscompilation.

**Fix.** `assert(!changed)` after the final iteration. A correct fixed-point
algorithm runs as long as needed; the cap exists only as a runaway-loop
guard.

### MED-8 — `computeFreeVars` re-walks entire module each iteration
**[ID-C12 — confirmed]** — `ir.cc:286-292, 299-328`.

`computeOne(fid)` recomputes the per-Block ref-set every iteration. For
nixpkgs-scale modules this dominates compile time.

**Fix.** SCC-aware fixed point that re-visits only functions whose
dependents changed.

### MED-9 — `m.recVarOrigins.push_back` copies the whole names vector per ref
**[ID-C9 — confirmed]** — `lower.cc:184`.

Every ref to a rec-attrset slot copies `recAttrsNames`. O(N²) per let-rec
on the names data alone.

**Fix.** `shared_ptr<vector<SymbolId>>` or a single `RecVarOrigin` per
`(func, recVar)` pair.

### MED-10 — `ir::Formal::defaultBlock` used as bool, set to magic `1u`
**[ID-C8 — confirmed]** — `lower.cc:576`, `emit.cc:781`.

`ifm.defaultBlock = fm.def ? 1u : ir::kInvalidBlock;` — `1u` doesn't point
at the actual default-expression block. emit.cc treats it as a presence
flag. Comment claims it's a real block id.

**Fix.** Change the field to `bool hasDefault` or record the real default
block / FuncId.

### MED-11 — `tlBridgeFallbackExpr` (PARTIAL: nesting save/restore is correct)
**[ID-B2 — partial]** — `primops.cc:86`, `v3_hook.cc:885-901, 958-974`.

The save/restore at v3_hook.cc DOES nest correctly. Narrower concern: the
per-entry stored fallback in `BridgeAttrEntry`/`BridgeListEntry`/`BridgeClosureEntry`
captures whatever the TLS value was at registration time, which is correct;
but if a fallback re-run itself builds new bridges, it relies on the
re-run keeping the TLS in sync. Severity drops to low after critic
verification.

### MED-12 — `isV3CacheCandidate` mutated via const_cast on shared AST
**[ID-B3 — confirmed]** — `v3_hook.cc:188, 1068`.

Once `skipPermanently` clears the flag, it stays cleared for the whole
process. `EvalState::parseFile` shares parsed AST across states. Two
evaluators with different hook configurations on the same AST mis-behave.

**Fix.** Move the candidate flag into a `std::unordered_set<const nix::Expr *>`
keyed in v3, leaving the AST node logically immutable.

### MED-13 — `setNixEvalState` set on null only; never cleared
**[ID-B4 — confirmed]** — `primops.cc:96, 2298, 2436, 2523, 2598, 5343`.

If a different EvalState later calls into a v3 primop, the wrong state is
used. Single-evaluator CLI is fine; library consumers (hydra, LSP) are not.

**Fix.** Always overwrite (`tlNixEvalState = &ns`) at bridge entry; add
`ScopedNixEvalState` RAII.

### MED-14 — Lazy-attr / lazy-list / lazy-closure bridge tables grow unboundedly
**[ID-B7 — confirmed]** — `primops.cc:2226, 2254, 2261, 2745, 2828, 2903`.

Static `std::vector`s, never-removed entries. Long-running daemons accumulate.
Compounds with CRIT-4 / ID-B1: tables hold Value payloads invisible to Boehm.

**Fix.** Either weak-key the entries by an arena handle, or clear in
`~EvalState`. Combined with CRIT-4 fix.

### MED-15 — Fiber stacks 16 MiB heap with no guard page
**[ID-B8 — confirmed]** — `fiber.cc:144-152, fiber.hh:70`.

`posix_memalign(pageSize, 16 MiB)`. No PROT_NONE guard. Stack overflow
silently corrupts adjacent heap (likely arena blocks). Comment drift:
`fiber.cc` mentions 64 MB, `fiber.hh` says 16 MB.

**Fix.** Restore the mmap'd PROT_NONE guard page. The prior attempt's
failure was unrelated.

### MED-16 — Per-bridge-primop `static thread_local VMState` is leaky
**[ID-B11 — confirmed]** — `primops.cc:2358, 2396, 2441, 2526, 2601, 2948`.

Five separate thread-local VMStates declared independently. `.reserve()`
doesn't clear; an exception during a bridge call leaks frames into the
next invocation.

**Fix.** Stack-allocate the VMState (small enough); the `.reserve()` was
about preventing reallocation during the call, not persistence.

### MED-17 — Force-hook RecBuild path allocates fresh Bindings* per force
**[ID-B16 — confirmed]** — `v3_hook.cc:1136-1187`.

Every force that has a RecBuild upvalue source allocates a fresh
`Bindings*` plus N bridge thunks. Tree-walker's Env is identity-stable;
v3 throws away identity.

**Fix.** Memoize per `(envId, freeVarSet)`.

### MED-18 — `OP_FORCE` App-resolve uses C-recursion via `forceValue`/`callClosure`
**[ID-R13 — confirmed]** — `vm.cc:1778-1786`.

Each level adds a C++ frame. Long App spines (`mapAttrs (mapAttrs (mapAttrs …))`)
blow C-stack first. Each `callClosure` also `Alloc::allocClosure`s a synthetic
closure for primop dispatch (the GC critic's miss).

**Fix.** Loop in C until v is no longer App; accumulate spine in a local
vector; one batch invocation. Mid-term: implement Apps as opcode-level.

### MED-19 — `NIX_V3_RETURN_CHAIN` and `CFF_FORCE_RETRY` overlap
**[ID-R8 — confirmed]** — `vm.cc:1604, 1964`.

OP_FORCE always sets CFF_FORCE_RETRY before pushing the thunk frame. With
`NIX_V3_RETURN_CHAIN=1`, the chain push fires and `break`s, bypassing
caller-resume that consumes the flag. The flag is set but never observed
in that mode.

**Fix.** Delete the chain-push code outright. After this much soak time
(WC38_FIX_PLAN.md confirms it's not the WC-38 fix), keep the env var as a
tombstone in WC38_FIX_PLAN.md only.

### MED-20 — Static primop pointers initialised before `GC_add_roots`
**[ID-G3 — confirmed]** — `primops.cc:2728-2741, 2811-2824, 2886-2899`.

Pattern: `pv = ns.allocValue(); pv->mkPrimOp(po); lazyListPrim = pv; GC_add_roots(...)`.
Race window between alloc and root registration.

**Fix.** `static Value * const lazyListPrim = []{ ...; GC_add_roots(...); return pv; }();`
— root is registered *before* the static is observed.

### MED-21 — `v3CallFunctionHook` declared but never installed
**[ID-B5 — confirmed-LOWER]** — `eval.hh:770`, `eval.cc:1834-1835`.

Tree-walker checks the slot on every callFunction; v3 never assigns it.
Cost is one null-pointer compare per call — negligible. Either implement or
remove the slot.

### MED-22 — `pendingFiber` TLS save/restore on nested fibers
**[ID-B10 — confirmed-LOWER]** — `fiber.cc:99-126, 181-188, 206-216`.

Walking carefully through `fiberCreate`/`fiberResume`/trampoline: pendingFiber
is set immediately before swap, read on first instruction in trampoline,
cleared. Single-threaded per-thread, no race window. The original
"subtly racy" is overstated. The mild concern remaining: `activeFiberDriverDepth`
is checked only by `primV3CallBridge1`, not symmetrically by
`primV3ForceAttr` / `primV3ForceListElem`.

## 6. Low-severity / dead code / nitpicks

Grouped to keep the report scannable. Each item is real but small.

**Dead opcodes / IR variants / fields:**
- `OP_LOAD_SLOT_REF` (ID-R6, ID-C6) — Phase-3, dispatched but never emitted; `vm.cc:2570`.
- `OP_NOP` (ID-R7) — never emitted; `vm.cc:754`.
- `ir::PosExpr`, `ir::Negate`, `ir::RecAttrSet` (ID-C5) — emit stubs exist;
  not produced by lowerer. `ir.hh:166-170, 220-221, 241`.
- `ir::WithLookup::depth` (ID-C3) — emitted with value 0, ignored at runtime.
- `ir::With::slotRef` (ID-C6) — Phase-3 scaffolding.
- `Block::params` (ID-C4) — read by two consumers, never written; `ir.hh:330-337`.
- `kInvalidFunc` (ID-C7) — defined, never used.
- `bridge_yield.cc:70-76 FiberDone case` (ID-B9) — unreachable per its own comment.
- `primV3CallBridge2` (ID-B18) — defined, never registered as primop;
  `primops.cc:2415-2484`.

**Dead diagnostic / env-var probes on hot path:**
- `dbgLogForceSite` call setup (ID-R15) — cost is one branch with cold call,
  small.
- 11 `NIX_V3_*` / `V3_DBG_*` probes in vm.cc (cross-cutting). Worth a
  centralized debug-config struct.

**Comment / encoding drift:**
- `OP_ATTRS_INIT_DYN` doc says `[nStatic:16, nDyn:8]`; actual encoding is
  `[nStatic:12, nDyn:12]` (ID-R10, also missed by other reviewers — same
  documentation point).
- `fFlags` truncation `uint32_t → uint8_t` (ID-R9). First flag added at
  bit 8+ silently disappears.
- `primSeq` no longer forces first arg; comment one refactor behind (ID-B13).
- `bool` round-trip via `payload.i == 1` only (ID-B19) — singletons only,
  no construction discipline enforced.

**Minor perf:**
- `materializeWord` re-allocates Value per tagged-int touch — small int
  cache would amortize. (Picked up by both v2 and v3 reviewers.)
- `OP_APPLY_OVERRIDES` emitted unconditionally for every let-rec (ID-C14).
- `unit.symbolTable = ir::globalSymbolTable()` copies entire global table
  per CU (ID-C15).
- `static std::deque<std::string>` pools in `lowerString`/`lowerPath`/
  `interpStr` leak across runs (ID-C17).
- `lowerLetRec` final return wraps result in redundant `VarRef` (ID-C18).
- `lowerWith dynamic_cast` where kind-check + static_cast suffices (ID-C19).
- Bridge primop chain construction in lazy attrs/lists is N×O(allocate-per-element)
  (ID-B20).
- `treeWalkerToV3` calls `yieldForceTreeWalker` before type switch even on
  WHNF values (ID-B12).
- `m.varOrigins` accumulates duplicates (ID-C10).

**Brittleness:**
- `OP_RETURN`'s self-cycle check covers direct `Tag::Thunk` only, not
  Tag::App or Tag::Slot back-references (ID-R16). Backstop is the chase-iter
  cap.
- `mergeBindings` doesn't dedup b against itself (ID-R17). Tree-walker has
  the same assumption; likely fine.
- `OP_GET_LOCAL` skips bounds check by design (ID-R18). Documented.
- `OP_FORCE` chase-iter counter resets on retry-goto (ID-R19). Backstop is
  frame-depth limit.
- `Slot` write-back inconsistency between `forceValue` and `OP_FORCE`
  slow path (ID-R14).
- `OP_ATTRS_SELECT` IC `Bindings*` reuse (ID-R12) — only matters if the
  arena ever frees, which is currently never.
- `lowerCompileAndPopulate` permanent caching even on throw (ID-B14) —
  intentional poisoning; arguably fine.
- `Bridge` Tag::Thunk shortcut bypasses cycle map (ID-B15).
- Closure-bridge / formal-attrset gating duplicated (ID-B17) — drift risk.
- Arena lacks destructor / `GC_remove_roots` (ID-G2) — fine for single-thread,
  bites multi-threaded use.

## 7. Cross-cutting patterns

**Pattern A — GC blind spots in non-arena, non-Boehm storage.**
CRIT-2, CRIT-3, CRIT-4, HIGH-6, MED-14, the missed bridge-table-storage
hazard, and the missed arena-Huge-fallback hazard (alloc.hh:187-191) are all
the same architectural issue: containers of `Value` living in storage Boehm
doesn't scan. The arena is correctly registered (`alloc.hh:225`) and
explicitly-rooted statics (`primops.cc:2740/2823/2898`) are correct, but
everything else assumes "Boehm finds it via the C-stack scan" — which works
*until* a GC happens at exactly the wrong moment.

The discipline the codebase needs: **every Value container is either in the
arena, registered as a root, or uses `traceable_allocator`. No exceptions.**
This deserves a dedicated audit pass, not piecemeal fixes.

**Pattern B — Eager force at emit time vs lazy at consume.**
MED-5 (the WC-38 territory), MED-2 (tail-call peephole missing the then-branch
because of trailing OP_FORCE), and MED-18 (App-resolve C-recursion) all
descend from the same compile-time-force regime. Every `forceVal()` site in
lower.cc emits an OP_FORCE; the runtime then re-forces on consume; the
peephole gives up because the trailing instruction isn't OP_CALL anymore.
Removing emit-time forces simultaneously fixes the laziness regressions and
unlocks the missing tail-call optimisation.

**Pattern C — TLS / static state with no boundary reset.**
MED-12 (`isV3CacheCandidate`), MED-13 (`tlNixEvalState`), MED-16
(`static thread_local VMState`), and MED-14 (bridge tables) all assume
single-EvalState, single-thread, no-exception semantics with no
"EvalState boundary" reset hook. Library consumers (hydra, LSP, test
harnesses) that create and destroy multiple EvalStates on the same thread
are at risk.

**Pattern D — Phase-N scaffolding never collected.**
At least 9 dead IR variants / opcodes / fields / primops trace back to
abandoned or deferred Phases. Each adds icache pressure, dispatch table
size, and confusion for the next maintainer. A single cleanup commit could
remove all of them with negligible risk.

## 8. What the reviewers missed (caught by critics)

1. **`OP_SET_LOCAL` companion footgun to ID-R18** — `vm.cc:844`,
   `idx < vm.valueStack.size() - 1` underflows on empty stack. The
   runtime reviewer flagged GET; the SET sibling has the same shape.

2. **`clearBlackMarksOnException` doesn't clear `CFF_FORCE_RETRY`** —
   `vm.cc:3140`. Adjacent to MED-3. After unwind, frames at exitDepth keep
   the flag, and their next OP_RETURN may trigger spurious force-retry on
   stale value.

3. **`callClosure` in OP_FORCE App chase also allocates a Closure per resolve**
   — `vm.cc:3613`. MED-18 flagged C-stack growth; missed the per-attr
   Closure alloc that nixpkgs-style `mapAttrs` chains pay.

4. **`mergeBindings` doesn't update `recordAttrPos` for the merged result**
   — `vm.cc:319-339`. Calling `builtins.unsafeGetAttrPos` on a merged-attr
   would return null where tree-walker returns the per-attr pos.

5. **Bridge-table std::vector storage twin to CRIT-4** — already incorporated
   into MED-14.

6. **Arena Huge fallback `std::malloc` at `kHugeCutoff`** — `alloc.hh:187-191`.
   Allocations > 4 MB skip Boehm entirely. Adjacent to CRIT-4.

7. **`OP_ATTRS_INIT_DYN` documentation drift** — `bytecode.hh:117`. Already
   in low-severity section as ID-R10.

## 10. Open questions for the user

These came up across the agents and are worth the user's call:

1. **`NIX_V3_RETURN_CHAIN`** — still A/B testing or deprecated? Several
   findings (MED-19, ID-R6) simplify drastically if it can be deleted.
2. **`v3CallFunctionHook`** (MED-21) — unfinished WC-14 follow-up, or
   genuinely abandoned? If abandoned, drop the slot from `EvalState`.
3. **`BRIDGE_CLOSURE` + `FIBER`** — keep as switchable scaffolding indefinitely,
   or land/strip? The branching adds real test-matrix surface (ID-B17 may
   already be a regression that nobody noticed because BRIDGE_CLOSURE is off
   by default).
4. **Disk cache currently in production use?** CRIT-1 only fires through the
   serializer's remap path. If yes, this could explain transient flake-eval
   bugs after warm-cache loads — a probe test would be cheap and high-signal.
5. **Bridge tables' lifecycle** (MED-14) — short-lived processes only, or
   long-running daemons? Determines whether the fix is "clear in `~EvalState`"
   or "weak-key entries".
6. **Identity preservation for tagged ints** — the `materializeWord` per-touch
   alloc loses `Value*` identity. Is this acceptable since ints are
   equality-by-content, or a correctness goal?
7. **Test coverage for missed cases** — would you like me to draft regression
   tests for: HIGH-4 (`inherit (trace ...)` side-effect count), HIGH-1
   (cross-closure tail call with `with`), HIGH-3 (`<` on list of `map id …`
   elements)?
