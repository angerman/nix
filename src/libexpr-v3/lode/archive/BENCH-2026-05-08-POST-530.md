# v3 perf — post-#530 (lexical-with chain landed)

Date: 2026-05-08
System: aarch64-darwin (M4)
Comparand: in-tree TW (`build/src/nix/nix eval`)
Tools: `src/libexpr-v3/test/bench-eval-only.sh` (V3_TIMING phase
split + NIX_VM_STATS hook entries to surface VM-vs-FFI breakdown).

The user's framing for this report:

> The goal is to make sure `<eval>` is faster than TW. The
> `<compile>` can be amortized (e.g. if we eval the same nixpkgs
> over and over and over again).

So we measure **`v3.run` (just the dispatch loop wall) vs TW total
wall**, since v3's lower+compile is amortizable via the disk cache
on production workloads.

| 25 | 34ms    | 82ms   | 2.4x  |

**v3 VM is ~2.4× slower than TW on tight compute-bound loops, with
0% FFI back to TW** (`v3 force stats: forceEntries=0`,
`bridge=0.000`).  The slowdown is uniformly per-instruction in the
dispatch loop — it's not amortizable as workload size grows.

## VM-vs-FFI breakdown

`NIX_VM_STATS=1 V3_TIMING=1` reports for each eval:

```
v3 hook stats:  evalEntries=N cacheHits=H cacheMisses=M
v3 force stats: forceEntries=N forceHits=H forceMisses=M
v3 hook timing (ms): lower=L compile=C run=R bridge=B
```

For all the synthetic workloads above, including the lib.foldl'
nixpkgs-lib case:

- `evalEntries=1` → one top-level entry (the v3-direct path).
- `forceEntries=0` → TW never re-enters v3 mid-eval; v3 owns the
  whole evaluation after the entry.
- `bridge=0` → no time spent in TW callbacks.

Conclusion: **on these workloads, v3 is the sole evaluator.  The
slowdown is purely VM overhead, not FFI.**

## Where the VM time goes (compute-bound case)

For `fib(32)`:
- v3.run = 2366ms
- TW.eval ≈ 971ms (TW total minus process startup)
- v3 / TW ≈ 2.4x

`fib` is `f n = if n<2 then n else f(n-1) + f(n-2)` — the dominant
opcodes are `OP_GET_LOCAL`, `OP_LIT_INT`, `OP_LESS`, `OP_BRANCH_FALSE`,
`OP_SUB`, `OP_ADD`, `OP_CALL`, `OP_TAIL_CALL`, `OP_FORCE`,
`OP_RETURN`.  No attrsets, no `with`, no primops.  Pure dispatch
loop overhead.

The ratio is uniform across n=25..32, so the cost is proportional to
instruction count, not setup or allocation.

### Mechanical pair (recommended next sprint)

Items #5 and #8 are zero-prerequisite, zero-risk wins that
SPECIFICALLY target the fib/ackermann shape (tight dispatch loop
with arithmetic):

- **#5 Direct threading**: replace the 0x100-entry `switch` in
  `vm.cc dispatchLoop` with a `&&label_OP_X` computed-goto table
  under `#ifdef __GNUC__`.  Mechanical, no semantic changes.
  Existing planned task #431 / #477.
- **#8 Typed numeric opcodes**: emit `OP_ADD_II / OP_SUB_II /
  OP_MUL_II / OP_EQ_II` when both operands are statically int.
  Saves 3 branches per arithmetic op — directly attacks fib's
  inner loop.

Together these should close ~10-15% of the 2.4x gap on fib.

### Foundational pair (unlocks #2/#3/#4/#6)

Per OPT_OCCUR_PLAN, the first thing to build is occurrence analysis
(~250 LOC, ~4 days).  No direct user-visible perf number, but every
non-mechanical win above depends on it.  The use-def map is a
follow-on (~300 LOC).

### What v3 has now

- 6 IR optimization passes: constant folding, CSE, redundant-Force
  elim, alias inlining, primop fusion, DCE.  All pass-by-pass
  block-local except DCE (fixed-point).  All soundness-first.
- Emit-time superinstructions: `OP_GET_LOCAL_FORCE`,
  `OP_GET_UPVALUE_FORCE`, fast-path `OP_IS_*` / `OP_HEAD` / etc. for
  ~14 primops.
- Selector lambda specialisation (#424; arity-1).
- 4-way attribute-select inline cache (PIC).
- Native intrinsic dispatch for `lib.fix` / `extends` /
  `composeExtensions` (#495 + STG-13).

### What v3 lacks (and why fib is slow)

- No occurrence analysis → no informed inliner; alias-inlining only
  collapses VarRef chains, not single-use lambdas.
- No demand analysis → every thunk is allocated even when forced
  on every path.  fib's recursive calls cause one Thunk per call
  even for arguments that are immediate Int constants.
- No selector thunks → repeated attrset access doesn't cache.
- No hidden-class shapes → every attrset is a sorted-name binary
  search.
- No direct threading → 0x100 switch dispatch with predictable
  miss penalty on M-series.
- No typed numeric opcodes → every `+` / `-` / `<` does
  Tag-test + force chase + Int-vs-Float dispatch.

## 2026-05-09 update — root cause of fib slowness

After landing #538 (run optimise() on v3-direct path), per-OP cost
stays at ~11.4 ns/op and fib(30) ratio is still 3.1× TW.  Per-call
v3 emits **50 bytecode ops** for fib's body (`if k < 2 then k else f
(k - 1) + f (k - 2)`).  Direct dump (`V3_DUMP_AT_START=1`) for
`f(5)`:

```
L[2] code=[5..80) nUp=1 nLocals=18 name=k   ← one frame per recursive call
  [5]  GET_LOCAL_FORCE 0     ← force k
  [6]  SET_LOCAL 1            ← stash forced(k)
  [7]  LIT_INT 2              ← push 2
  [8]  SET_LOCAL 2            ← stash 2
  [9]  GET_LOCAL 1            ← retrieve forced(k)
  [10] GET_LOCAL 2            ← retrieve 2
  [11] LESS                   ← compare
  [12] SET_LOCAL 3            ← stash result
  [13] GET_LOCAL 3            ← retrieve for branch
  [14] BRANCH_FALSE 17
  ... (analogous for both `f (k-1)` and `f (k-2)` calls plus the
       `+`)
```

The 11.4 ns/op figure is *not* the dispatch loop overhead — it's
the cost of the lowerer producing more ops than necessary.  Of the
50 ops per fib call, **~15-20 are pure stack-shuttle SET_LOCAL/
GET_LOCAL pairs** carrying single-use values between bindings.
The IR is in A-normal form: every sub-expression gets a binding,
every binding gets a slot, every slot gets SET after compute and
GET before use.

A minimal-shape fib body should be:
```
GET_LOCAL_FORCE 0    ← force k
LIT_INT 2
LESS
BRANCH_FALSE else
GET_LOCAL 0         ← then: return k
JUMP end
else: GET_UPVALUE 0 ; REC_BINDING_SLOT_REF f
GET_LOCAL_FORCE 0 ; LIT_INT 1 ; SUB ; CALL
GET_UPVALUE 0 ; REC_BINDING_SLOT_REF f
GET_LOCAL_FORCE 0 ; LIT_INT 2 ; SUB ; CALL
ADD
end: RETURN
```
~20 ops.  We're at 50 — a 2.5× bloat.  This precisely matches the
2.4× v3/TW ratio observed.

### Actionable

The mechanical pair (#5/#8) helps each surviving op run faster.
But the **dominant** opportunity is **the optimizer eliminating
single-use bindings** so the bytecode emits fewer ops in the first
place.  This requires:

1. **Occurrence analysis** (`opt_occur.cc`,
   OPT_OCCUR_PLAN_2026-05-08.md, ~250 LOC).  Foundation.
2. **`inlineTrivialBindings` extension**: when a binding's RHS is
   a literal (`LitInt/Bool/Null/...`), substitute fresh copies at
   each use site (literals have zero evaluation cost; safe to
   duplicate).
3. **Single-use binding elimination**: for `OnceLinear` bindings
   whose RHS is a pure expression, substitute at the use site.
   Either move the RHS bytecode emission to the use site, OR
   post-emit peephole that elides `SET_LOCAL N; ...; GET_LOCAL N`
   when slot N is single-use (verified via slot-reference scan).

Estimated cumulative impact: cut fib body from 50 → ~25 ops, ~2×
speedup on compute-bound v3 code.  Combined with #5 (computed
goto, ~10% per remaining op), v3 should reach **TW parity or
better on fib**.
