## Headline

**Architecture is converging; defaults are regressing.**

The STG-* push is doing real work, not just bisecting:
- STG-8 cell-update at OP_RETURN is a permanent GHC `stg_IND` analogue
- STG-10 single-VM re-entry collapses cross-VMState BlackHole pathology
- STG-13a/b/c native Extends/Compose intrinsic dispatch
- STG-14a direct v3 dispatch for TW lambdas with v3 bodies

These are default-on (or default-on-when-recognised) and shrink the
TW round-trip surface concretely.  But the **kill-switch flags**
under `NIX_V3_STG=1` (publish/recovery/hooks disabled) are needed to
get default-mode perf back to where it was three days ago — fib30
went from "~5 % faster than TW" to "~68 % slower than TW" in the
default path because of the publish-walk and side-table-recovery
added to fight the identity-bug class.  The fix exists (STG-1) but
is flag-gated until #498 root-causes.

Meanwhile the FFI grew from 9 % → 23 % at the declaration level but
**zero production call sites route through any FFI implementation**.
The optimizer pipeline is unchanged.  EvalState dependencies are flat
or growing.  Shapes — the headline structural recommendation from the
last three reviews — are still not started.

## Recommended next sprint (rewritten post-Phase-1)

**Strategic frame.** The v3 VM was never about speeding up TW.
Pure v3 is the goal. The bridge that dominated this review's body
(`primV3CallBridge1`, `__v3_force_attr` / `__v3_force_list_elem`,
`Tag::Bridge` handling, the bridged-thunk peek paths — every entry
in §1.2 and §1.4 of the bridge inventory) exists because v3 is
integrated as a hook *inside* TW. Under `NIX_V3_DIRECT_EVAL` (Phase
1, just landed) v3 is the host and the bridge is bypassed, not
fixed. The recommendations below are ordered around **drop
reliance on TW as early and as soon as possible**.

In order of leverage × cost:

### 1. Fix the next v3-direct blocker: `with`-scope upvalue capture

`(import <nixpkgs> {}).hello.name` under `NIX_V3_DIRECT_EVAL=1`
fails at `OP_WITH_LOOKUP: name 'nix-update' not found in with-scope`
(`pkgs/top-level/all-packages.nix:28`, `with pkgs;` followed by
`inherit (nix-update) nix-update-script;` at line 196).  Same
wrong-upvalue-capture shape as #528 but for `with`-captured names.
Probably wants a similar widening of the `with`-scope thunkify gate
or analogous slot-capture-vs-eager-eval timing fix.  This is the
gating bug for "nixpkgs evaluates under v3-direct"; everything
else is downstream.  ~1–3 days.

### 2. Phase 2 — flake installables under v3-direct

Per `INVERSION_PLAN_2026-05-08.md` Phase 2a: keep flake resolution
in TW (it's already TW machinery on the store + fetcher side); do a
*one-shot* TW→v3 bridge once the resolved attrset is available;
run v3-direct from there onward.  The conversion already exists
for results; the inverse direction (TW Value → v3 Value at a
single boundary) is the missing piece.  Lets `nix eval
nixpkgs#hello.name` work under v3-direct.  ~1 week.

### 3. Phase 3 — extend `NIX_V3_DIRECT_EVAL` to other CLI commands

`nix build`, `nix run`, `nix-instantiate` each have their own eval
entry.  Each gets the same gate as `CmdEval::run` did in step 3
(`cd490979f`).  Mechanical, mostly copy-paste with per-command
output handling.  ~3–5 days for the major three; iterate the long
tail later.

### 4. Phase 4 — formalise the v3 → TW leaf-callback direction

When v3 hits a primop it doesn't implement (genuine store/IO,
`derivationStrict`'s strict merge, `builtins.path { filter = …; }`,
fetchers), it calls TW with concrete TW Values.  This is the only
direction the bridge needs to support after the inversion completes.
**`applyClosure` is the right primitive for the *inverse* of that**
— when TW invokes a v3 closure as a callback (filter functions,
`genericClosure` operators) — and finally has a real production
caller.  Migrate `builtins.path { filter = …; }` through
`applyClosure` first; rest follow.  This is also the milestone
where the FFI stops being decorative.  ~1 week.

### 5. Mechanical perf wins (still cheap, still valid)

PR2 computed-goto (~1 day, +15–20 %) and typed numeric opcodes
(`OP_ADD_II`, …, ~1 day, +3–5 %).  Recommended for **three sprints
in a row** without landing.  Independent of the inversion track;
lands cleanly any time someone touches `vm.cc`.  See `vm.cc:2`
comment.

### 6. Hook-mode is now maintenance, not critical path

The hook-mode path remains active by default for backward
compatibility and for code paths not yet ported to v3-direct.  The
publish-walk perf regression in default mode (Agent 5: fib30 1.68×
slower than TW) and the always-thunkify root cause (#498) still
need closing for users who haven't switched, but **these are
maintenance items now**.  Once Phases 2–4 are in place hook mode is
deprecated and eventually deletable.  Specifically, the previous
recommendations to "close STG-12" and "default-on STG-1" stay open
as bug-fix items but drop from critical-path priority.

### 7. Documentation refresh

Update `USAGE.md` for the new `NIX_V3_DIRECT_EVAL` and the 6
missing env vars (`NIX_V3_STG`, `NIX_V3_STG_KEEP_HOOKS`,
`NIX_V3_NO_TW_LAMBDA_INV3`, `NIX_V3_NO_EARLY_PUBLISH`,
`V3_DBG_TW_LAMBDA_INV3`, `V3_DBG_RETRY`).  Refresh real-world perf
numbers under v3-direct.  Correct the lowering-gap inventory in
REVIEW_2026-05-06 (path-interpolation belongs to the runtime
store-bridge column, not lowering).  Half a day.

### 8. Foundational: occurrence analysis (`opt_occur.cc`)

~3 days, ~250 LOC.  Strict precondition for any structural
optimizer work this quarter (selector thunks, demand analysis,
heuristic inliner).  Should land before shapes (#1 of the 8 ranked
optimizer recommendations).  The optimizer track is parallel to the
inversion track and doesn't block it — schedule independently when
capacity allows.

## Verdict (rewritten post-Phase-1)

**The strategic frame is now correct in code, not just in plans.**
`INVERSION_PLAN_2026-05-08.md` and Phase 1 (4 commits + 26-shape
regression) explicitly position v3 as the host and TW as the leaf —
exactly the architecture that retires the bridge surface this
review's body audited.  The original headline ("Architecture is
converging; defaults are regressing") was true of the hook-mode
path; under v3-direct, both halves matter less — the regressing
defaults live in a path that's being deprecated, and the
architecture has already converged via inversion rather than via
bridge fixes.

**The pure-v3 timeline shortened dramatically.**  Three reviews ago
the worry was parity.  One review ago it was decorative FFI.  This
review's worry was "default-mode performance regressed and the fix
is gated on a not-yet-root-caused bug."  Today's reality:
**Phase 1 of the inversion landed today.**  `nix eval --expr` /
`--file` is already v3-direct under one env var.  Phases 2–4
(flake installables, other CLI commands, leaf TW callbacks) are
concrete and incremental.  Pure-v3 in 1–2 weeks for the `eval`
path, 3–4 weeks across the major CLI commands, is realistic.

**The bug class hasn't gone away — it surfaces directly now.**
#528 was the first v3-direct blocker; the with-scope upvalue
capture is the second; the always-thunkify root cause (#498) is
the third.  All three are wrong-upvalue-capture under deep
nesting.  The same root cause that the hook-mode path masked (and
partly created via the publish-walk recovery) now shows up as
named bytecode failures.  That's progress: the failures are
legible.  Shapes (V8 hidden classes, the headline structural
recommendation across three reviews) become more attractive once
these bugs are root-caused — the underlying issue is identity
stability, exactly what shapes solve.

**Critical path:** fix the with-scope upvalue capture, then ship
Phase 2.  `applyClosure` migration is the *Phase 4* concrete goal
(TW invoking v3 closures, the only direction that survives the
inversion), not a hook-mode patch.  STG-12 (the hook-mode bridge
force-throw) and default-on STG-1 (the hook-mode publish-walk
regression) drop from critical-path to maintenance.

If the next sprint isn't **"land the with-scope fix, ship Phase 2,
extend Phase 3 to one more CLI command,"** the inversion will
stall in a half-migrated state where some commands run v3-direct
and others don't — the worst of both worlds.  The clear win is
within reach: **drop reliance on TW as early and as soon as
possible.**
