# FFI audit — TW fallback inventory + migration plan

**Date**: 2026-05-20. **Status**: design + measurement plan; not committed work.

This audit answers three questions:
1. What is v3's current TW fallback (where do we still cross into TW)?
2. How large is the FFI surface (LoC, call sites, primop count)?
3. What can move into the VM without violating V3-NATIVE (LESSONS §1.1) or v3-native-primops correctness (LESSONS §1.2)?

**Includes self-correction**: an earlier draft incorrectly classified system-info primops (`currentSystem`, `nixVersion`, `langVersion`, `storeDir`, `currentTime`, `nixPath`) as system-boundary FFI. They're not — they're immutable per-process / per-eval constants that should be injected as Values at v3 init. See §5.0.

## 1. Premise

After Phase 1 closed and Phases A-H IR optimization landed, v3 still talks to TW through six distinct mechanisms. The team's recent Pillar 2 sprint (#695 getFlake bridge, #696 IFD via realisePath, both 2026-05-20) added new FFI for cardano-node — *legitimate* system-boundary work. But the existing FFI surface deserves an audit:

- Which of v3's 109 primop wrappers actually need to remain TW-bridged?
- How many `treeWalkerToV3` / `v3ToTreeWalker` conversion sites fire per real eval?
- Where would moving more into the VM yield perf without re-litigating the V3-NATIVE constraint?

The constraint hierarchy stays as established:

- **V3-NATIVE** (LESSONS §1.1): v3 owns evaluation; TW is permitted ONLY at FFI leaves (store, paths, derivations, file I/O, eval-state parse).
- **v3-native primops are CORRECT** (LESSONS §1.2): pure-data primops (`map`, `filter`, `foldl'`, `attrNames`, etc.) stay v3-native. Marshalling v3 Values ↔ Boehm-managed TW Values is per-call expensive AND crosses GC ownership.

This audit categorizes each TW dependency against those constraints.

## 3. Six TW dependency mechanisms

| # | Mechanism | Necessary? |
|---|---|---|
| 1 | `NIX_V3_SKIP_INSTALLABLE_PREEVAL` opt-out default | **NO** — drift; Stage 2 work |
| 2 | `bridgeBuiltin<N>` primop wrappers (9 primops) | YES — system-boundary fetchers / flake / filterSource |
| 3 | `bridge_yield.cc` TW-state yield protocol | Mostly — correctness shim for cross-VM-state callbacks |
| 4 | `treeWalkerToV3` / `v3ToTreeWalker` conversions (104 sites) | Mixed — depends on what's being converted and why |
| 5 | `primImport` → TW parser (extended with IFD today via #696) | Partly — Stage 9 module linking would retire most of this |
| 6 | Boehm GC = TW's allocator | YES today (LESSONS §1.6); Stage 3 nursery would replace for short-lived |

The biggest opportunity in this list is **#1** (drifted; needs explicit Stage 2 work) and **#5** (Stage 9). Both are architectural.

## 4. What MUST stay FFI (V3-NATIVE-immutable)

These primops have legitimate system-boundary reasons; moving them into v3 would violate V3-NATIVE:

| Category | Primops | Why they stay |
|---|---|---|
| **Fetchers** | `fetchurl`, `fetchTarball`, `fetchTree`, `fetchGit`, `fetchMercurial`, `fetchClosure`, `filterSource` | libfetchers' networking + caching + lock-file resolution — not portable into v3 |
| **Store ops** | `primPath`, `primPlaceholder`, derivation daemon-write step, `addToStore` paths | libnixstore daemon protocol |
| **File I/O** | `primReadFile`, `primReadDir`, `primReadFileType`, `primPathExists`, `primFindFile` | cppnix's sandboxed path resolution + symlink semantics + NIX_PATH integration |
| **Flake operations** | `getFlake` (today's #695), `primParseFlakeRef`, `primFlakeRefToString` | libflake's lock-file format + URI parsing + fetcher integration |
| **IFD** | `primImport` for derivation-context paths (today's #696) | `realisePath` invokes the build daemon |
| **Trace I/O** | `primTrace`, `primTraceVerbose` | stderr/logger integration with daemon |
| **Eval-state ops** | `tryEval`, `addErrorContext`, `unsafeGetAttrPos` | Manipulate v3's *own* state; "FFI in shape, v3-native in semantics" |

**Total justified FFI**: ~25 primops. Plus parser entry point + Boehm GC.

Note: `findFile` is in this list because it walks the filesystem searching NIX_PATH. It LOOKS like system info but is actually file I/O. Easy to confuse with the genuinely-immutable system-info constants in §5.0.

## 5. What CAN move into the VM

### 5.0 Tier 0 — Inject system-info as constants at v3 init (1-2 days; trivial)

**This was missing from the earlier draft.** These six primops are not FFI — they're immutable values per-process or per-eval:

| Primop | Value | Mutability |
|---|---|---|
| `builtins.currentSystem` | e.g. `"aarch64-darwin"` | Process-constant (config-time) |
| `builtins.nixVersion` | e.g. `"2.24.0"` | Compile-time constant |
| `builtins.langVersion` | int (currently 6) | Compile-time constant |
| `builtins.storeDir` | e.g. `"/nix/store"` | Process-constant (config-time) |
| `builtins.nixPath` | list of `{prefix, path}` attrsets | Process-constant (CLI/config-time) |
| `builtins.currentTime` | int (Unix epoch) | Per-eval constant (cppnix caches once per eval) |

Today these are registered as 0-arity primops that auto-invoke at attribute access. Each access: dispatch through TW's primop infrastructure, marshal the constant back to v3.

**Proposal**: at v3 init, query cppnix for each value, construct the corresponding v3 Value, and register them as ATTRIBUTES of `builtins` (not primops). Access becomes a direct attrset lookup. Zero FFI calls per access.

For `currentTime`: capture once at v3 init (matches cppnix's existing per-eval cache semantics). If cache-busting is needed for some niche use case, expose `__currentTimeUncached` as an explicit primop that does the I/O.

For `nixPath`: it's a list of `{prefix, path}` attrsets — slightly more complex to construct but still trivial (~20 LoC).

**Implementation cost**: ~1-2 days. Touches only the primop-registration site + v3 init. Zero risk to ongoing correctness work.

**Wins**:
- 6 fewer primop wrappers (109 → 103).
- Per-access dispatch removed; attribute-lookup fast-path applies.
- The eventual Stage 9 (module linking) work gets a cleaner separation between "constants v3 owns" and "operations v3 bridges."

### 5.1 Tier 1 — Architectural (large; sequenced via ROADMAP)

**T1.A: Retire `NIX_V3_SKIP_INSTALLABLE_PREEVAL` default-on** — the only 🔻 drift item on the scorecard. ROADMAP Stage 2. ~6 weeks at original estimate; less at observed velocity. Closes the biggest TW dependency by share-of-work.

**T1.B: Stage 9 module linking** — replaces `primImport`'s TW parse with v3-native parse → lower → compile pipeline. `LINKING_DESIGN_2026-05-17.md` 5-phase migration (L0-L4); ~5 weeks.

**T1.C: Stage 3 nursery default-on** — doesn't reduce primops.cc but eliminates Boehm-as-allocator for short-lived allocations. Different layer than the primop migration but same family of work.

### 5.2 Tier 2 — Bytecode-install more callback primops (~1-2 weeks)

Following the proven T0-T12 pattern. Callback-using primops benefit (callbacks live in bytecode; no TW round-trip per call):

| Primop | Why a candidate | Effort |
|---|---|---|
| `primSort` | Comparator callback; hot in attrset/lib iteration | ~2 days |
| `primGenericClosure` | Operator callback; used by `lib.fix`, module system | ~2 days |
| `primZipAttrsWith` | Combiner callback; used by `lib.recursiveUpdate` | ~1-2 days |
| `primFunctionArgs` (if not already) | Pure data + simple — check | ~0.5 day |
| `catAttrs` (T17 reverted; recheck if it uses key-selector callback) | If yes, install; if pure C transform, leave | ~1 day verify |

**Total: ~1-2 weeks** for 3-5 more primops.

### 5.3 Tier 3 — Opcode-ify pure arithmetic / string primops (~1 week)

Push hot pure-data primops down to OP-level dispatch (inline in vm.cc):

| Primop | Why opcode | Effort |
|---|---|---|
| `primBitAnd`, `primBitOr`, `primBitXor` | Pure arithmetic; small impl | 1 day |
| `primFloor`, `primCeil` | Pure float ops | 0.5 day |
| `primParseInt` | Pure parsing; small | 1 day |
| `primSplitVersion` | Pure string parsing; hot in version compares | 1 day |
| `primBaseNameOf`, `primDirOf` | Pure path string ops | 0.5 day |
| `primStringLength` (if not already an op) | Trivial | 0.25 day |

**Total: ~1 week.** Follows the existing `OP_HEAD` / `OP_TAIL` / `OP_LENGTH` / `OP_ELEM_AT` pattern. **Caveat per LODE_REVIEW D4b**: opcode-inline duplication requires `// keep in sync with primops.cc:NNN` anchors.

### 5.4 Tier 4 — Heavyweight (defer; ROI uncertain)

| Item | Effort | Why defer |
|---|---|---|
| `primFromJSON` / `primToJSON` v3-native | 1-2 weeks | Needs JSON library (rapidjson / simdjson); real wins only on JSON-heavy workloads (`--json` flag) |
| `primHashString` / `primHashFile` v3-native | 1 week | Modest wins; libcrypto dependency |
| `primToXML` v3-native | 1-2 weeks | Used in NixOS module eval; heavy impl |
| `primMatch` / `primSplit` v3-native | 3 days | `std::regex` already C++; verify marshalling actually crosses TW first |

Revisit Tier 4 after Stage 5/6 (shapes + PICs) land — the optimization landscape may shift which primops are hot.

## 6. Measurement spike — which 104 cross-sites actually fire?

The 104 `treeWalkerToV3` / `v3ToTreeWalker` call sites is a STATIC count. The DYNAMIC count per eval is what matters for prioritization.

**Proposed spike** (~1 day):
- Add a per-call-site counter gated behind `V3_DBG_TW_CROSS=1`.
- Each `treeWalkerToV3` / `v3ToTreeWalker` invocation increments its site's counter.
- Run representative workloads (hello.name, hello.drvPath, full nixpkgs `attrNames`, cardano-node M5 once it lands).
- Dump at exit: top-N hot sites + call counts.

The hot sites become the targets for migration:
- If a hot site is in a callback-using primop → bytecode-install (Tier 2).
- If a hot site is in a pure-data primop → opcode-ify (Tier 3).
- If a hot site is in something legitimately system-boundary → leave alone (V3-NATIVE-compliant).

This spike is small (~1 day) and informs all of Tiers 1-4. **Highest-leverage single measurement available right now.**

## 7. Strategic ordering against current work

| Track | Items | Why now / why later |
|---|---|---|
| **Now (parallel with TW-parity sprint)** | Tier 0 (system-info as constants); Tier 3 (opcode-ify pure arithmetic) | Each item is small, isolated, low-risk; doesn't conflict with the correctness work; can land per-PR. Tier 0 is especially trivial (~1-2 days for all 6) |
| **Now (parallel measurement)** | V3_DBG_TW_CROSS spike | 1 day; informs Tier 2/3/4 prioritization; pure measurement, no code risk |
| **After correctness convergence** (per §1.7 signals) | Tier 2 (bytecode-install more callback primops) | Each medium-risk; needs stable foundation; follows proven T-series pattern |
| **Sequenced via ROADMAP** | Tier 1 (Stage 2 + Stage 3 + Stage 9) | Each is large architectural work; sequenced per ROADMAP_TO_VISION |
| **Deferred** | Tier 4 (JSON, hash, XML, regex) | Revisit after Stage 5/6 land |

**Honest single recommendation for the next 1-2 weeks**: Tier 0 + V3_DBG_TW_CROSS spike + Tier 3 (start). Total ~1 week of work; produces concrete wins + the measurement data to drive Tier 2 prioritization. All compatible with the ongoing TW-parity sprint per §1.7 (each piece is correctness/capability, not perf-on-moving-target).

## 8. Self-critique

Following LESSONS §1.7 discipline:

**(C1) The system-info classification error.** My earlier audit lumped `currentSystem`, `nixVersion`, `langVersion`, `storeDir`, `currentTime`, `nixPath` into "System info — must stay FFI." The user correctly pointed out these are immutable data; they should be injected as v3 Values at init, not bridged. This is exactly the kind of error that comes from pattern-matching ("these are system-y; system stuff is FFI") rather than thinking about the actual data lifetime. Codifying the correction here so future analyses don't repeat.

**(C2) Effort estimates are typically 30-50% optimistic for me.** Tier 0 "1-2 days" is probably 2-3 days realistic. Tier 3 "1 week" is probably 1.5 weeks. Use the conservative end for planning.

**(C3) The 104 cross-site count is static; dynamic count is what matters.** Without the V3_DBG_TW_CROSS spike, prioritization between Tier 2 and Tier 3 is guesswork. The spike must happen before scheduling Tier 2/3 work — otherwise we'd be optimizing cold paths.

**(C4) Tier 2's bytecode-install pattern assumes the callback round-trip is the bottleneck.** It probably is for hot callback primops, but verify per-primop before committing. LESSONS §4.11 codifies that non-callback primops don't benefit; same rule applies to "rarely called callback primops."

**(C5) The "v3-native primops are CORRECT" rule (§1.2) is sometimes mis-read as "more v3-native = better".** Not so. v3-native is correct for pure-data ops; FFI is correct for system boundaries. The right framing: each primop has a *correct location* (v3-native OR opcode OR bytecode OR FFI). The audit identifies which is which.

**(C6) Tier 0 is so obviously correct in retrospect that I should have surfaced it without prompting.** This is a lesson about audit discipline: when classifying, ask "does this depend on system state that can change during eval, or is it captured-once?" not "is this called 'system info'?"

**(C7) `currentTime` as a per-eval constant is technically a behavioral choice.** cppnix's documented behavior is per-eval cache; v3 would match. But: some niche use cases (CI test patterns, certain `builtins.trace` debugging) might rely on per-call freshness. Risk is small. Expose `__currentTimeUncached` if anyone complains. Don't gold-plate by default.

**(C8) The bigger architectural question is "what does v3-direct mean?"** Today it's "v3 evaluates after TW pre-eval." After Stage 2 it's "v3 evaluates from parse-output directly." After Stage 9 it's "v3 evaluates from cached cells directly." Each stage moves the meaning of v3-direct further from TW. This audit serves all three.

## Summary in one paragraph

v3 today has ~1 015 LoC of explicit FFI infrastructure + ~3 500 LoC of implicit TW-using paths in primops.cc, with 104 static `treeWalkerToV3`/`v3ToTreeWalker` conversion sites and 109 primop wrappers. The current TW fallback decomposes into 6 mechanisms (TW pre-eval default-on, `bridgeBuiltin<N>` system primops, `bridge_yield.cc`, Value conversions, `primImport` parser, Boehm GC). Roughly 25-30 primops legitimately stay FFI (fetchers, store, file I/O, flake, IFD, trace, eval-state); the other ~75-80 are v3-native or can move further into the VM. **Immediate wins available**: Tier 0 system-info constants (~1-2 days; 6 primops removed); the V3_DBG_TW_CROSS measurement spike (~1 day; informs all further prioritization); Tier 3 opcode-ification of small pure primops (~1 week). **Architectural wins via ROADMAP**: Stage 2 (retire pre-eval; the single biggest 🔻 drift item), Stage 9 (module linking; retires primImport-via-TW-parse), Stage 3 (nursery default-on; retires Boehm-as-allocator for short-lived). The Pillar 2 work (today's #695 + #696) added new FFI for cardano-node — correctly, since those are genuine system-boundary operations.
