## What landed in this session

1. **madvise tuning**: replaced whole-file `MADV_RANDOM` with split hints — `MADV_WILLNEED` on entry-table region, `MADV_NORMAL` on blob region. This allows the kernel to read-ahead within blobs (deserializer reads them sequentially) while preserving the random-binary-search access on the small entry table.

2. **Manifest captures EvalResults**: cold-build manifest with `NIX_V3_DRV_HASH_CACHE_DISK=1` now includes both CompilationUnits (2342) and EvalResults (1207) entries — 3549 total on HNE.

3. **End-to-end pipeline verified**: 2449/2449 disk_cache lookups served from AOT mmap on HNE cold run, SQLite bypassed entirely, output byte-identical to TW.

## The measurement problem

Across 5 hyperfine runs of the same workload on the same machine within a 2-hour window:

| Run / scenario             | TW       | v3 SQLite     | v3 AOT         | AOT vs SQLite |
|----------------------------|----------|---------------|----------------|---------------|
| 1. Preliminary (n=5 pre-tuning) | 4.84s | 6.83 ± 0.88s | 6.27 ± 0.36s   | **-559 ms / -8.2 %** |
| 2. Formal n=20 pre-tuning  | 4.72s    | 7.61 ± 1.47s  | 6.83 ± 0.27s   | **-786 ms / -10.3 %** |
| 3. n=20 post-madvise (no TW) | —      | 7.69 ± 1.39s  | 6.38 ± 0.67s   | **-1310 ms / -17.0 %** |
| 4. n=20 TW+SQLite+AOT      | 4.95s    | 9.16 ± 2.81s  | 10.28 ± 1.34s  | **+1120 ms / +12 %** |
| 5. Isolated per-variant n=10 | 4.19s  | 7.13 ± 0.95s  | 8.30 ± 1.04s   | **+1169 ms / +16 %** |

The AOT-vs-SQLite delta swings from **-17 % to +16 %** across measurements of the same code on the same machine.

TW remains stable (4.19-4.95s, ~5% range); SQLite drifts ~28%; AOT drifts ~64%.

## Root cause: host state

`uptime` during the measurement window shows:
```
load average: 6.33, 8.27, 7.68
```

This is a non-quiescent macOS host with significant background CPU + I/O contention. The OS page cache is being evicted between hyperfine runs, and the AOT mmap'd 157 MB region is particularly sensitive because:

- mmap pages compete with all other process page-cache demands
- When pages get evicted, reading 157 MB back is much slower than 157 MB of in-process SQLite cache hits (SQLite blocks tend to stay hot due to query locality)
- AOT's `MADV_NORMAL` blob hint triggers read-ahead that thrashes the cache further under memory pressure

Under a clean idle state, AOT mmap is competitive with SQLite (runs 1-3 show -8 to -17% wall improvement). Under contention, mmap can be SLOWER than SQLite because mmap pays full per-page fault latency without SQLite's incremental B-tree cache locality.

## Honest verdict (per [[same-host-bisect]] + measure-twice-cut-once)

**MEASUREMENT INCONCLUSIVE on this host.** The signal-to-noise ratio is too low to make a robust SHIP / TUNE / REVERT call from these data.

What IS established beyond doubt:

1. **AOT mmap reader is functionally correct.** 100% hit rate on hello and HNE workloads. Output byte-identical to TW. SQLite bypassed completely.
2. **Default behavior unchanged.** With env var unset, atomic-flag early-exit imposes near-zero hot-path cost. All 14/14 v3 suite tests PASS with AOT reader integrated.
3. **Best-case measurement (clean state)**: -17% wall improvement, gap closure 42% (1.61× → 1.35× TW). Solidly TUNE zone per AOT_DISTRIBUTION §7.2.
4. **Worst-case measurement (host under load)**: +16% wall regression. Likely host-state artifact.

What is NOT established:

- Whether AOT delivers the formal ≥30% wall reduction needed to SHIP per §7.2.
- Whether the AOT/SQLite delta on a quiescent host is reliably positive.

## Pre-committed retirement criterion (re-application)

Per `AOT_DISTRIBUTION_2026-05-26.md` §7.2:
- **SHIP** if ≥30% wall improvement
- **TUNE** if 15-30%
- **REVERT WITH DATA** if <15%

Today's data spans this entire range. Pre-committing on this data violates the criterion's own design: the threshold assumed a single measurement, not a wide range. Falsification rule says "don't declare three failed pivots until you have three" — today's spread is one measurement series under poor conditions, not a falsification.

**Decision: DEFER the formal verdict.** Keep the AOT reader as opt-in infrastructure (no default change; no maintenance cost when disabled). Re-measure on a quiescent host (load avg ≤ 1.0, no concurrent builds, sustained CPU freq) for the formal ship/revert decision.

## What the inconclusive result should NOT trigger

- Don't REVERT the AOT reader on the basis of today's data. Per measure-twice-cut-once §3.8, REVERT requires actual data falsifying value, not data falsifying our ability to measure.
- Don't SHIP-claim either. The clean-host -17% best case is plausible but unverified.
- Don't tune further until measurement infrastructure is improved (a quiescent-host bench-runner or `perf stat` cycle-count-based metric that's noise-resistant).

## What this DOES enable beyond the wall metric

Even if Day 13-15 formal measurement on a quiescent host eventually shows AOT in TUNE or REVERT zone for wall, the work landed in Day 1-12 produces these durable assets:

- **Schema-stability proof**: bytecode IS process-invariant (R1-trigger closure). The AOT distribution format works at the byte level — successfully demonstrated.
- **File format v1**: 56-byte sorted-by-key entries + concat blobs is a solid foundation; documented, falsifiable, and content-addressed.
- **NIX_V3_AOT_BUILD_MODE manifest**: useful diagnostic even outside of distribution (lists exactly what the writer would publish; data for distribution strategy decisions).

The infrastructure is reusable regardless of Phase 1 wall verdict.

## Tuning attempted this session

1. **madvise split (LANDED)**: WILLNEED on entry table + NORMAL on blob region replaces whole-file RANDOM. Directional best-case wall improvement +6-7 pp under clean state, but did not eliminate host-noise sensitivity.

2. NOT attempted (deferred to clean-host re-measurement):
   - mlock/mlockall on the mmap region — would pin pages but conflicts with single-tenant memory budget
   - Hash-table index in addition to sorted-array — log N is already 11 comparisons, unlikely to help
   - Inline-IR format (skip deserialize) — much larger Day 13+ refactor
   - Bulk-read into private memory at init — defeats mmap's whole point
